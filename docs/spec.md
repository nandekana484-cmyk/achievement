# 現場実績入力・稼働率可視化Webアプリ 開発指針

- 版: 0.3(2026-10-21 既存アプリのすべての月次DBを読む方式に変更。想定タクトの書式、正規化、削除フラグの扱いを反映)
- 位置づけ: このアプリを作るときの**唯一の基準**。企画書・アーキテクチャ設計書(初版)と食い違う場合は、この文書を優先する
- 読み手: 開発者と、開発を手伝うAIアシスタント

## 0. AIアシスタントへの指示(必ず守ること)

1. **既存の生産管理アプリのDBには絶対に書き込まない。** 読み取りは「計画の取得」モジュールからだけ行い、読み取り専用で開く
2. **時刻はすべてサーバーで記録する。** ブラウザやタブレットの時計を記録に使わない
3. **実績は物理削除しない。** 誤りは訂正履歴(audit_log)を残して直し、取り消しは状態で表す
4. **権限はすべてのAPIでサーバー側が検査する。** 画面の表示制御だけに頼らない
5. **ボタン操作は冪等にする。** 端末は操作ごとに一意のリクエストIDを送り、同じIDの再送は1件として扱う
6. **「11. 未確定事項」に載っている内容は勝手に決めない。** 仮置きで実装する場合は、コードに `TODO(要確認): <項目名>` を残す
7. 動作環境はWindowsの1台のPCで、**1プロセスで動かす前提**。クラウドや外部サービスは使わない
8. 依存ライブラリを追加するときは、理由とライセンスを書く。**GPL・AGPLのライブラリは使わない**
9. 画面の文言は日本語。用語は「2. 用語集」に従う
10. 既存アプリの仕様が分からないところは推測で埋めず、質問する

---

## 1. 目的と範囲

現場がタブレットのボタンで作業の開始・終了・数量を入力し、管理者がラインの計画と実績、進捗率、稼働率をリアルタイムに見られるようにする。実績は既存の生産管理アプリへ戻し、計画と実績が一致した状態を保つ。

- 試行は1ラインで行う。後に全ラインへ展開する
- 既存アプリは作り替えない。既存アプリ側の改修は、実績の取込口に限る

## 3. 動作環境と運用の前提

- **本番**: 担当者PC(Windows)。サーバー専用機はない。クラウドは企業方針で使わない
- **開発**: 開発者PC。担当者と開発者は(現在は同一人物だが)別人として扱う。本番データを開発者PCに置かない
- **利用端末**: 現場のタブレット、管理用のPC。どちらも社内LAN経由でブラウザから担当者PCに接続する
- **既存アプリ**: 担当者1人が担当者PCで使う。実データはローカルSQLite。共有フォルダにはバックアップだけを置く
- **将来**: 全ライン展開時に、社内LANに置く専用ミニPCへ移せる構成にする(パスやポートは設定ファイルに出す)

## 5. ドメインルール

### 5.1 キッティングNo.

形式: `ファイルNo.-回-生産ライン-発行年月日-その日の発行順`

例: `0722-2-S-251014-01`

| 部分 | 例 | 意味 |
| --- | --- | --- |
| ファイルNo. | 0722 | 生産機種 |
| 回 | 2 | 1=1回目、2=2回目 |
| 生産ライン | S | ラインのコード |
| 発行年月日 | 251014 | 2025-10-14(**生産日ではない**) |
| 発行順 | 01 | その日の発行順 |

- 取込時に5つに分解して保存する。計画の識別キーは、既存アプリと同じ **「キッティングNo.+ロットNo.」**
- 回は既存DBの面(production_side)を正とし、キッティングNo.の回と食い違ったら警告する。ラインも同様に実装ライン(mounting_line)を正とする
- 正規表現は例から推定したもの(`^([^-]+)-([12])-([^-]+)-(\d{6})-(\d+)$`)。各部分の桁数は実データで確認する。形式に合わない番号は取り込まずに警告を出す
- **日程だけの変更では番号は変わらない。数量などの内容の変更では番号が振り直される**

### 5.2 計画データの項目

既存アプリの月次DBの `kitting_plan_items`(1行=1計画=1面)から読む。詳細: docs/design/legacy-integration.md

| 本アプリの項目 | 既存DBの列 | 備考 |
| --- | --- | --- |
| キッティングNo. | kitting_list_no | |
| ロットNo. | lot_no | |
| 品名 | board_name | |
| ファイルNo. | setup_file_no | 既存アプリと同じ正規化をかける(下記) |
| ライン | mounting_line | 既存アプリと同じ正規化をかける(下記) |
| 回 | production_side | "1"=1回目、"2"=2回目 |
| 数量 | planned_qty(REAL) | その面の予定生産数。整数でなければ警告 |
| 累計 | cumulative_qty_external | |
| 発注数 | order_qty | |
| 計画開始・終了 | plan_start_datetime / plan_end_datetime | 書式 `2026/07/01 00:00:00`(日本時間として扱う) |
| 納期 | deadline | |
| 削除 | delete_flag | **考慮しない。** 保存するだけで、取消や変化の判定には使わない |
| 状態 | status | 保存するだけ(本アプリの判定には使わない) |
| 想定タクト(takt_sec) | master.db `production_side_master.takt_time`(TEXT) | ファイルNo.・実装ライン・面ごと。中身は小数の数値("30"、"55.72" など)。数値にできない・マスタに無いときは空にして警告。単位は要確認(仮置き: 1枚あたりの秒) |

- **正規化**: ファイルNo.と実装ラインは、既存アプリ(models/production_side_master.py)と完全に同じ規則で正規化する(`domain/normalize.py`)。ファイルNo.: NFKC(全角→半角)→前後の空白を除く→数字だけなら文字列のまま4桁にゼロ埋め(`"4"`→`"0004"`、`"00004"`→`"00004"`)、それ以外は大文字。ライン: NFKC→前後の空白を除く→大文字。想定タクトの検索、キッティングNo.のライン記号との比較も、正規化した値どうしで行う
- **削除フラグ**: 業務上の意味が分からず、実データでもすべて0のため考慮しない
- 既存DBの created_at / updated_at は `YYYY-MM-DD HH:MM:SS`(PCのローカル時刻=日本時間)。正とするDBの決定(6.1)に使う

既存DBには actual_start_datetime / actual_end_datetime(実際の開始・終了)の列もある。実績の反映で埋めるかどうかは、実績の取込口の仕様と一緒に決める。

- 数量: この計画で生産する数(既存アプリは実績登録時の数の確認にこの列を使う)
- 累計: これまでに生産した累計(既存アプリの値を正とし、本アプリで足し込まない)
- 発注数: ロット全体の数
- 想定タクトは回ごとに異なる(表と裏で違う)

### 5.3 組(1回目と2回目)

- 組のキー: **ロットNo. + ファイルNo. + 数量**。品名は確認用(食い違ったら警告)
- 1回目か2回目かは、キッティングNo.の回の部分で判断する
- 同じロットを別の日に分けて作ることは多いが、同じ日に同じロット・同じファイルNo.・同じ数量の計画が重なったことはない。万一重なった場合は、発行日と発行順が早いものどうしを組にし、管理画面に警告を出す

### 5.4 回の工程

各回で、次の工程の開始・終了を記録する。段取りと片付けは回ごと(表と裏で別々)に行う。

詳細: docs/design/run-records.md(5.4〜5.8 の実装の判断の理由。冪等性、二重の記録の防止、完了の写し、board の付帯作業の扱いなど)

| 工程 | step_type | 入力 | 必須 |
| --- | --- | --- | --- |
| 段取り | setup | 開始・終了 | ○ |
| N1チェック | n1_check | 開始・終了 | ○ |
| 生産 | production | 開始・終了・生産数(区切りごと) | ○ |
| 初品チェック | first_article | 開始・終了 | ○ |
| X線検査 | xray | 開始・終了 | 省略あり |
| 片付け | cleanup | 開始・終了 | ○ |
| NG数 | (run_inputs: ng_qty) | 数値(回ごと) | |
| 備考 | (run_inputs: remark) | 自由記入 | |

ルール(`services/run_records.py`。違反は 409 と、画面にそのまま出せる日本語の理由):

- **生産の区切り**: 画面は「生産開始」「生産終了(生産数)」を繰り返し押す形にし、区切り番号(seq)は計画×工程ごとに1から自動で振る。2回目以降の区切りを開始するときは、再開理由(理由マスタのうち「生産の再開理由として使える」もの)が必須。1回目の生産とほかの工程では再開理由を受け付けない
- **再開理由の設備**: 2回目以降の生産の開始で、設備が必要な再開理由(マシントラブルなど)を選んだときは、設備(equipment_id)を任意で受け付ける(計画のラインの有効な設備であること)。それ以外の場合は受け付けない。ライン画面用の取得(board)でも返す
- 生産の終了は生産数(0以上の整数)が必須。ほかの工程の終了では生産数を受け付けない
- 区切りは記録用紙の欄が3つなので、画面上の目安は3回。**データ上は上限を設けない**
- **工程は繰り返し記録できる**(例: トラブルで別の計画に切り替え、戻ってから段取りをやり直す。seq が2になる)
- 異なる工程どうしは時間が重なってよい(例: 生産中に初品チェック)
- 工程の記録・生産数・備考・完了は、**キッティングNo.(計画のまとまり)の単位**で記録する(ロットNo.を使わない)
- 同じキッティングNo.の同じ工程で、終了していないものがあるのに開始はできない(生産の区切りどうしも重ならない)。終了していないものが無いのに終了はできない。DBにも「終了していない記録はキッティングNo.×工程で1件まで」の一意制約を持たせ、同時の操作でも二重に記録しない
- **NG数だけは、ロットとNGが出た面を選んで入力する**(記録: 入力した画面の計画のキッティングNo.、ロットNo.、面、NG数、入力者、日時)。同じ「キッティングNo.+ロットNo.+面」の入力は最新の値を有効とし、過去の値は履歴として残す
  - 選べる面: 面1の計画では面1だけ。面2の計画では面2と、同じロットNo.・同じファイルNo.の面1の計画が見つかるときの面1(見つからなければ面1は選べない)
  - 面1のNGには、対応する面1の計画のキッティングNo.も記録する(既存アプリに返すときに使う)
- 計画が無ければ 404。取消の計画は開始できない(終了はできる)
- 時刻はサーバーの時計で記録する。記録者の決め方は 5.6
- NG数は行を追加し、最新の値を有効とする(上書きしない)。備考は追加する
- 詳細: docs/design/run-records.md(NGで面を区別する理由、既存アプリの保存の形への変換)
- 計画をまたぐ重なりは基本的にないが、トラブルで今の計画を止めて別の計画を生産することはある。計画の順番の入れ替えもある(最終的に生産がそろえばよい)

API:

| メソッド | パス | 本文 |
| --- | --- | --- |
| GET | `/api/runs/{kitting_no}` | (計画のまとまり1件の状態) |
| POST | `/api/runs/{kitting_no}/steps/{step_type}/start` | request_id、restart_reason_id?、equipment_id?、operator_id? |
| POST | `/api/runs/{kitting_no}/steps/{step_type}/end` | request_id、produced_qty?、operator_id? |
| PUT | `/api/runs/{kitting_no}/ng-qty` | request_id、lot_no、side(NGが出た面)、ng_qty、operator_id? |
| POST | `/api/runs/{kitting_no}/remarks` | request_id、text、operator_id? |

**冪等性**(0-5): すべての操作で request_id を送る。同じ request_id の再送には、最初の応答をそのまま返す(200)。同じ request_id で内容が違えば 409。ルール違反で失敗した操作は記録しないので、同じ request_id で送り直せる(`services/idempotency.py`、表 api_requests)。

### 5.5 付帯作業(ライン単位)

計画の合間に起きる、ラインを止める出来事。**計画には結びつけず、ラインに記録する。**

生産の区切りの再開理由と、付帯作業の種類は、共通の理由マスタ(reasons)で持つ(マシントラブルの合計時間を、計画の中か合間かに関係なく集計できるように)。初期データ(マイグレーション 0004):

| 理由 | 区分 | 追加の入力 | 付帯作業 | 再開理由 |
| --- | --- | --- | --- | --- |
| 部品探し | ロス | | ○ | ○ |
| 欠品 | ロス | | ○ | ○ |
| マシントラブル | ロス | 設備を選ぶ(そのラインの設備。必須) | ○ | ○ |
| 立上立会 | ロス以外 | | ○ | |
| 応援・その他 | ロス以外 | | ○ | |
| その他トラブル | ロス | 理由の記入(必須) | ○ | ○ |
| 人員交代 | ロス以外 | | | ○ |
| トラブル停止 | ロス | | | ○ |
| 計画切替 | ロス以外 | | | ○ |

- 理由の列: name、name_vi(ベトナム語の名前。空を許す。7.5)、category(loss=ロス / non_loss=ロス以外)、counts_in_utilization(稼働率に含めるか)、requires_equipment、requires_text、usable_as_line_event、usable_as_restart、active、sort_order
- 開始・終了と、開始した人・終了した人を記録する
- **稼働率の計算からは外すのが既定**。理由ごとに「稼働率に含めるか」の設定を持ち(初期値はすべて含めない)、定義が決まったら切り替えられるようにする
- 種類はマスタで追加・変更できるようにする(今は開発用のコマンド `python -m app.cli` で一覧だけ。管理画面で作る)
- 生産の再開理由として使うときは、理由の記入は求めない。設備が必要な理由でも、設備は任意(5.4)

ルール(`services/line_events.py`。違反は 409):

- 「付帯作業として使える」理由だけ選べる。設備が必須の理由ならそのラインの設備が必須、記入が必須の理由なら記入が必須
- 同じラインで同じ理由の付帯作業が終了していないのに開始はできない。異なる理由どうしは重なってよい
- 計画を選んでいなくても開始できる。記録者の決め方と冪等性は工程と同じ

API:

| メソッド | パス | 本文 |
| --- | --- | --- |
| POST | `/api/lines/{line_code}/events/start` | request_id、reason_id、equipment_id?、reason_text?、operator_id? |
| POST | `/api/lines/{line_code}/events/{event_id}/end` | request_id、operator_id? |

### 5.6 誰がやったか

- すべての記録に、開始した人と終了した人を別々に持つ(人員交代で変わるため)
- ラインごとに「今の担当者」を設定し、ボタン操作の記録に自動で付ける。担当者は始業時と人員交代時に切り替える。1回の操作だけ別の人にすることもできる
- 実装(`services/line_operators.py`): 表 line_operators に履歴を持つ。交代すると前の行に end_at を入れ、新しい行を足す(今の担当者はラインに1人。すでに同じ人なら何も変えない)
- 記録者 = 本文の operator_id(本アプリの中の番号)か worker_id(作業者ID)のどちらか。指定が無ければラインの今の担当者。どちらも無ければ 409「担当者が設定されていません」
- **作業者は既存アプリの master.db の workers から読み込む**(計画の同期のたびに。読み取り専用。計画の表が無いなどで計画の同期がエラーになっても、workers が読めれば作業者は読み込む)。名前・役割(admin / operator)・有効/無効を既存アプリに合わせ、既存アプリから見えなくなった作業者は消さずに無効にする(過去の記録が参照しているため)。作業者IDは既存アプリの表記のまま持ち、全角・半角と大文字・小文字の違いを無視して比べる(`domain/worker_id.py`)。正規化すると重なるIDは、片方を取り込まずに警告を出す
- legacy_app_dir が設定されていない環境(開発用)だけ、開発用コマンドで作業者を足せる(`python -m app.cli operators add <名前> --id <作業者ID>`。source=local)
- 担当者は**作業者IDで呼び出す**(PIN は付けない。11. 未確定事項)。画面では作業者IDの入力欄を一番上に置き、Enter(または「呼び出し」)でIDと名前を表示して確かめてから決める。入力欄はタブレットの文字キーボードが出る形で、将来の社員証のバーコードリーダー(文字の入力 + Enter)でも動く。名前の一覧(名前順。IDも並べる)から選ぶ方法も補助として残す
- 同じ名前の人がいても区別できるよう、画面の上部や記録の表示では名前の横に作業者IDも出す

| メソッド | パス | 説明 |
| --- | --- | --- |
| GET | `/api/lines/{line_code}/operator` | 今の担当者(未設定なら null) |
| PUT | `/api/lines/{line_code}/operator` | 交代する(本文: request_id、operator_id か worker_id) |
| GET | `/api/operators/lookup?worker_id=` | 作業者IDで、有効な作業者を呼び出す(無ければ 404「作業者IDが見つかりません」) |

ラインの記号は、既存アプリと同じ規則で正規化してから探す(`s` → `S`)。ラインは計画の同期で新しい記号を見つけたら自動で登録する(名前は「<記号>ライン」)。

### 5.7 完了と実績の反映

- **片付け終了 = その回の完了。** このとき次を行う
  - その回の稼働率を計算して保存する
  - その時点の計画数と想定タクトを、実績と一緒に保存する(後で計画が変わっても、過去の稼働率や日報が変わらないように)
- **製品の最終の回が完了したら、既存アプリへ実績を反映する**
  - 製品の完成数 = 最終の回の生産数(区切りの合計)。1回目と2回目を足さない
  - NG数は回ごとに分けて返す(既存アプリが回ごとに持っている)
- 完了後の誤りは、管理者が訂正し(訂正履歴を残す)、区分「訂正」で再出力する
- 実装済み(run_completions。キッティングNo.の単位): 片付けの終了で1件作る。生産数=区切りの合計、計画数(ロットの数量の合計)と想定タクトの写しに加えて、その時点のロットの一覧(ロットNo.・基板名・数量)と、ロットと面ごとの最新のNG数も写す。稼働率は定義が決まるまで空。片付けをやり直して終了したらもう1件作り、最新のものを有効とする。完了後も工程の記録は受け付ける
- 既存アプリはNGを「キッティングNo.+ロットNo.+面」で、面1 = 面1の欄 + 面2の欄 の形で持つ。この形への変換は、実績の反映の作業で作る(docs/design/run-records.md)
- ライン画面用の取得: `GET /api/lines/{line_code}/board?date=YYYY-MM-DD`(計画ごとの工程の記録・生産数の合計・最新のNG数・完了・計画の進捗率と、その日の付帯作業、今の担当者、ラインの進捗率)、`GET /api/masters?line_code=`(有効なマスタ)

### 5.8 進捗率と稼働率

- **進捗率**: 各ボタン操作で更新する。計画の進捗率 = 生産数の累計 ÷ その計画の数量。ラインの進捗率の定義は未確定
- **稼働率**: 片付け終了で更新する。定義は未確定(時間稼働率、生産数、想定タクトに対する実績のいずれか)。**定義に関わらず計算できるよう、工程・区切り・付帯作業の開始と終了、生産数、想定タクトを漏れなく記録しておく**
- ロット全体の進み具合は、既存アプリの累計と発注数を参照して表示する

## 6. 既存アプリとの連携

### 6.1 計画の取得(既存 → 本アプリ)

- 既存アプリのSQLiteを**読み取り専用**で開き(SQLiteのURIで `mode=ro`)、一定間隔(既定1分、設定で変更可)で計画を読む。読み取りは短く終える
- 既存DBの構造に依存する処理は `integration/legacy/`(入口は `integration/legacy_plans.py`)に閉じ込める
- 詳細: docs/design/legacy-integration.md(既存アプリの調査結果、正とするDBの決め方と取消にしない条件の理由)
- 差分は**自動で反映**する(計画は頻繁に変わるため、人の確認は挟まない)

**読むDB**(設定は既存アプリのフォルダ `paths.legacy_app_dir` だけ):

| ファイル | 扱い |
| --- | --- |
| `<既存アプリのフォルダ>\db\<フォルダ名>\inventory.db` | 月次DB(フォルダ名は自由)。**すべて読む**。ただし、ファイルの更新日時が `sync.legacy_db_max_age_days`(既定120日)より古いものは読まない |
| `<既存アプリのフォルダ>\db\inventory.db` | 「未選択」を表す既定DB。読まない |
| `<既存アプリのフォルダ>\db\master.db` | 共通マスタ(想定タクト) |

- どのDBも journal_mode=delete(WALではない)なので、読み取り中は既存アプリの書き込みを待たせる(既存アプリの待ち時間は30秒)。**DBごとに接続を開き、有効な計画とロットごとの最終書き込み時刻を1つの読み取りで取って、すぐ閉じる**
- 同期の記録(plan_sync_runs)に、その回に読んだDBの一覧と、DBごとの計画の件数を残す

**ロットごとに正とするDB**(`services/plan_source.py`):

実績は計画(キッティングNo.+ロットNo.)に付けるものなので、計画がどの月次DBにあるかにはとらわれない。棚卸の期間が重なり、既存アプリでDBを行き来することがよくあるため、同じロットが複数のDBにあるときは**ロットごとに、最後に書き込まれたDBを正とする**。

- ロットの最終書き込み時刻 = そのDBのそのロットの全行(無効な行も含む)の MAX(updated_at)
  - 既存アプリは、新しい版を作ると古い行の is_active と updated_at を更新し、新しい行は INSERT 時刻になる。削除(ソフト)も updated_at を更新する。前月からの引き継ぎ(ロット単位)でコピーした行は、コピーした時刻になる。実績の登録などでは計画の行は書き換えない
  - バックアップから戻したDBは元の時刻のままなので、正にならない
- 同じ時刻のときは、DBファイルの更新日時が新しいほうを正とする。内容が違えば警告を出す
- 同期で使う計画 = 各ロットについて、正とするDBの有効な計画だけ。正とするDBにそのロットの有効な行が無ければ(削除(ソフト)など)、そのロットの計画は「消えた」扱い
- 警告は、正とするDBの行のものだけを出す。どのDBの行か分かるよう、警告の先頭にDBのフォルダ名を付ける

**取消にしない条件**: 計画が正とするDBに無くても、次の場合は取消にせず、値も状態も変えない。

| 状況 | 扱い |
| --- | --- |
| 月次DBが1つでも読めなかった | 何も反映せず、同期の記録を error にする(どのDBが正か決められないため) |
| ロットがどの月次DBにも見当たらない(古くなって読まなくなった、など) | 取消にしない。警告を出す |
| 計画終了が今日の 0:00 より前 | 取消にしない(古い月次DBが読む対象から外れても、過去の計画を残すため) |
| 形式エラーで読めなかった行の計画 | 取消にしない(既存DBに行は残っているとみなす) |

取消にするのは、**ロットがどこかの月次DBにあり、かつ正とするDBにその計画が無いとき**だけ。

既存アプリの計画の持ち方(「版」方式):

- 計画を変えると、前の行を `is_active = 0` にして、`version` を1つ上げた新しい行を足す。行は削除しない
- 「キッティングNo.+ロットNo.」で有効な行は1件まで(部分ユニークインデックス)
- **内容が同じでも、取り込み直すと版が上がる。** したがって本アプリは `version` では変化を判定せず、**内容を比べて**判定する(`services/plan_diff.py`)
- 本アプリが読むのは `is_active = 1` の行だけ。キッティングNo.が空の保留行(pending_kitting_plan_items)は読まない

| 状況 | 扱い |
| --- | --- |
| 実績がない計画の変更・削除 | そのまま反映する |
| 実績がある計画の日程・数量の変更 | 計画の値を更新し、実績はそのまま |
| 実績がある計画が既存側で消えた | 実績は消さず、状態を「取消(実績あり)」にして警告する |
| 番号の振り直し(内容変更) | 下の「引き継ぎ」を行う |

**引き継ぎ**: 実績のある計画が消え、同じ同期でロットNo.、ファイルNo.、回が同じ新しい計画が現れたら、引き継ぎの候補とする。候補が1つなら実績を自動で新しい番号へ移し、複数なら管理画面で選んでもらう。元の番号と引き継ぎの記録は履歴に残す。

**安全装置**: 1回の同期で取消になる計画が多すぎるとき(既定は10件以上 かつ 分母の30%以上。設定で変更可)は、既存アプリのフォルダの設定間違いなどを疑い、何も反映せずに同期の記録を「反映を保留(guarded)」にする。

- 分子: この同期で取消になる計画の件数(上の「取消にしない条件」に当たるものは含まない)
- 分母: 有効な計画のうち、**計画終了が今日の 0:00 以降(または計画終了が空)のもの**。過去の計画は取消の対象にならないので、分母に入れると安全装置が効きにくくなるため除く

### 6.2 実績の反映(本アプリ → 既存)

- 連携フォルダにCSVを書き出し、既存アプリに新設する取込口で取り込む
- 書き手は一時ファイル名(`.tmp`)で書き終えてから `.csv` に改名する。読み手は `.csv` だけを読む
- ファイル名: `result_YYYYMMDD_HHMMSS_<出力ID>.csv`
- 出力IDで二重取込を防ぐ。出力の明細(どの実績をどの出力で渡したか)を記録する
- 文字コード、列、実績日の定義は未確定(「11. 未確定事項」)

## 7. 画面

### 7.1 現場画面(タブレット)

1. **ダッシュボード**: 生産ラインを選ぶ
2. **ライン画面**: 3カラム構成

```
┌──────────────────────────────────────────────┐
│ 上部: ラインの稼働率 / 進捗率 / 今の担当者        │
├────────┬──────────────────────┬───────────────┤
│ 左     │ 中央                 │ 右             │
│ メニュー │ タイムテーブル(縦軸が時刻) │ 選んだ計画の     │
│        │ ・計画の枠(最新の順番)    │ 工程ボタンと入力欄 │
│        │ ・実績(押された時刻)      │ ・付帯作業のボタン │
│        │ ・付帯作業のブロック      │               │
└────────┴──────────────────────┴───────────────┘
```

- タイムテーブルで計画をクリックすると、右カラムにその回の工程ボタンが表示される
- 計画の枠は最新の計画の順番で、実績は実際にボタンが押された時刻で描く(順番が入れ替わっても実績は動かない)
- 付帯作業のボタンは、計画を選んでいなくても押せる
- **表示範囲**: 稼働日の始まりの12時間前から、終わりの12時間後までの48時間(例: 稼働日 10/21 → 10/20 20:15〜10/22 20:15)。タイムテーブルの縦軸はこの48時間で、稼働日の境目(8:15)に線と日付を出す。開いたときは今の時刻のあたりまで自動でスクロールし、今の時刻の線はサーバーの時刻との差を補正して引く。表示範囲からはみ出す計画の枠は端で切り、切れていることが分かる印を付ける
- 画面は**キッティングNo.(計画のまとまり)の単位**。タイムテーブルの枠はキッティングNo.ごとに1つで、キッティングNo.・ロットの数(例: 3ロット)・計画数の合計を出す。右のパネルの見出しにロットの一覧(ロットNo.、基板名、数量、面ごとのNG数)を出す(多いときはパネルの中でスクロール)。NGは、ロットを選ぶ → 面を選ぶ(選べない面は押せない) → テンキーで数を入れる。入力済みのNGは一覧で見られる
- **ライン画面に出す計画**(有効な計画のまとまりのうち、次のどれか)
  1. 計画開始〜終了が表示範囲と重なる
  2. 表示範囲の中に実績の記録がある(先行して始めた計画)
  3. 作業を始めたが、片付けが終わっていない(日付は問わない。遅れている計画)
  - ただし、計画終了が過ぎたのに未着手の計画は出さない(検索で選ぶ)
- **ラインの進捗率**は、計画開始〜終了が稼働日(8:15〜翌8:15)と重なる計画で計算する(画面に出さない未着手で過ぎた計画も含める)
- **計画の検索**: 左のカラムの上の検索欄で、キッティングNo.・ロットNo.・基板名の一部で探す(`GET /api/plans/search?q=&line_code=`。英字の大文字・小文字と全角・半角の違いは無視。有効な計画のみ、計画開始が今に近い順に最大20件)。ロットNo.や基板名で当たっても、そのキッティングNo.のまとまりを返し、当たったところ(ロットNo.・基板名)を出す。結果を押すとその計画を選ぶ。キッティングNo.が完全に一致する計画が1件だけなら、Enter でそのまま選ぶ(将来のバーコードリーダーのため)。選んだ計画が表示範囲の外なら「表示範囲外の計画です(計画: 10/18 9:00〜)」と出す
- 担当者が未設定のまま記録のボタンを押したら、サーバーに送らず、先に担当者を選ぶ画面を出す
- 詳細: docs/design/line-screen.md(実装した画面の作り、ボタン操作の送り方、稼働日と表示範囲の理由、タブレット向けの決まり)

### 7.2 管理画面(PC)

- 日報: ラインの実績を24時間のガントチャートで表示する
- 計画の同期状況と警告(取消(実績あり)、引き継ぎの候補、組の食い違い、再印刷が必要)
- 実績の訂正(訂正履歴を残す)と再出力
- マスタ: ライン、設備、理由(停止理由・付帯作業の種類)、作業者、管理者
- 記録用紙の印刷

### 7.3 記録用紙

- A4縦1枚に、上半分が1回目、下半分が2回目
- **作業前に印刷して準備する。** 計画の情報を印字し、作業の記入欄を設ける
- 印刷はブラウザの印刷プレビューから行う(ワンクリック印刷は不要)。印刷用ページをReactで作り、CSSで `@page { size: A4; margin: 0 }` を指定する。日本語Webフォントを配信して見た目をそろえる
- 複数の製品を選び、1製品1ページで一度に印刷できるようにする
- 印刷後に計画が変わったものは、管理画面に「再印刷が必要」と表示する(印刷時の計画の値を記録して比較する)
- 試行中は一部の手書きを残す。**Webで入力する項目はWebの値を正とする**

### 7.4 QR読取

フェーズ1では作らない(タイムテーブルから選べるため)。選び間違いが目立った場合に、ハンディのバーコードリーダーでの読取を検討する。

### 7.5 表示言語の切り替え

- 現場画面は、日本語とベトナム語を切り替えられる。切り替えのボタン(「日本語 / Tiếng Việt」)は、ライン選択の画面と、ライン画面の上部に置く
- 選んだ言語は、その端末に記憶する(最初は日本語)
- 画面の文言は辞書(`frontend/src/i18n/ja.ts`。ベトナム語は `vi.ts`)に集め、画面のファイルに直接書かない。用語は日本語の辞書で「2. 用語集」に従う
- 訳さないもの: サーバーが返すエラーの文(409 / 404 / 503 の理由。日本語のまま出す)、計画の内容(キッティングNo.、ロットNo.、基板名など)、作業者とラインの名前
- 理由と設備の名前は、マスタのベトナム語の名前(name_vi)を出す。空なら日本語の名前を出す
- 日付と時刻は、どちらの言語でも同じ形(24時間表記、日本時間)
- ベトナム語の訳はレビュー役が用意する(初版は 2026-10-21 に取り込み済み)。新しく足した文言で訳がまだのものは「(未翻訳)」と日本語の文を出す
- 詳細: docs/design/i18n.md(仕組み、キーの付け方、文言を足すときの手順)

## 9. 非機能要件

詳細: docs/design/db-writes.md(書き込みのロックの背景とテスト)

| 項目 | 方針 |
| --- | --- |
| 同時アクセス | uvicornは1プロセス。SQLiteはWAL。端末数台を想定 |
| 書き込みのロック | SQLite は古い読み取りにもとづく書き込みを拒否する(busy_timeout があっても即座に database is locked になる)ため、本アプリのDBに書き込む処理(ボタン操作、計画の同期、開発用コマンド)は、処理の最初に書き込みのロックを取る(BEGIN IMMEDIATE)。あわせて、同じプロセス内の書き込みは1つのロックで1つずつ行う(`app/db/session.py` の `write_transaction`)。計画の同期は、既存DBの読み取りと正とするDBの決定をロックの外で行い、本アプリのDBに反映する部分だけをロックする。それでもロックが取れなかったとき(ほかのプロセスが書き込み中など)は 503「他の処理と重なったため、記録できませんでした。もう一度押してください」を返し、冪等性の記録(api_requests)には残さない(同じ request_id で送り直せば記録される) |
| 認証(現場) | 現場端末はライン単位で使い、記録者は「今の担当者」で特定する(PINの要否は未確定) |
| 認証(管理) | 個人アカウントとパスワード(ハッシュで保存) |
| HTTPS | フェーズ1は不要(カメラもPWAも使わないため)。必要になったら社内用の証明書を導入する |
| 時刻 | サーバーの時刻で記録する。担当者PCのWindows時刻同期を有効にする |
| バックアップ | SQLiteのバックアップ機能(`backup()` または `VACUUM INTO`)で、毎日定時と更新前に共有フォルダへ保存する。起動中のファイルコピーはしない |
| ログ | アプリのログはファイルに日ごとに分けて保存する |
| 障害時 | 担当者PCが止まっている間、現場は紙に記録し、復旧後に管理者が代理入力する(入力者と入力日時を残す) |
| 常時稼働 | タスクスケジューラ(またはWindowsサービス)で自動起動。稼働時間中はスリープ無効。IPアドレス固定。ファイアウォールはアプリのポートだけ許可 |

## 10. 開発・配布・運用

担当者PCのフォルダ構成:

```
C:\GenbaApp\
  app\v1.0.0\        実行ファイル(版ごとにフォルダを分ける)
  data\genba.db      本番DB
  data\config.toml   ポート、既存DBのパス、連携フォルダ、バックアップ先、同期間隔
  exchange\          連携フォルダ
  logs\
```

ビルド(開発者PC): フロントエンドをビルド → テスト → PyInstallerでまとめる → 版番号付きのzip

更新(担当者PC): 停止 → 新しい版のフォルダを置く(旧版は残す)→ 起動(起動時にバックアップとAlembicを自動実行)→ 稼働確認の画面で確認。問題があれば旧版と更新前のバックアップに戻す。

- delete_flag の扱い → 考慮しない(5.2)
