## 0. AIアシスタントへの指示(必ず守ること)

1. **既存の生産管理アプリのDBには絶対に書き込まない。** 読み取りは「計画の取得」モジュールからだけ行い、読み取り専用で開く
2. **時刻はすべてサーバーで記録する。** ブラウザやタブレットの時計を記録に使わない
3. **実績は物理削除しない。** 誤りは訂正履歴(run_corrections など)を残して直し、取り消しは取り消しの印で表す
4. **権限はすべてのAPIでサーバー側が検査する。** 画面の表示制御だけに頼らない
5. **ボタン操作は冪等にする。** 端末は操作ごとに一意のリクエストIDを送り、同じIDの再送は1件として扱う
6. **「11. 未確定事項」に載っている内容は勝手に決めない。** 仮置きで実装する場合は、コードに `TODO(要確認): <項目名>` を残す
7. 動作環境はWindowsの1台のPCで、**1プロセスで動かす前提**。クラウドや外部サービスは使わない
8. 依存ライブラリを追加するときは、理由とライセンスを書く。**製品に組み込むライブラリは GPL・AGPL を使わない。** ビルドのときだけ使う道具は、作った成果物に GPL が及ばない場合に限り使ってよい(例: PyInstaller はブートローダーの例外があるので可)。版の選び方と更新の記録: docs/design/dependencies.md
9. 画面の文言は日本語。用語は「2. 用語集」に従う
10. 既存アプリの仕様が分からないところは推測で埋めず、質問する

## 1. 目的と範囲

現場がタブレットのボタンで作業の開始・終了・数量を入力し、管理者がラインの計画と実績、進捗率、効率をリアルタイムに見られるようにする。実績は既存の生産管理アプリへ戻し、計画と実績が一致した状態を保つ。

- 試行は1ラインで行う。後に全ラインへ展開する
- 既存アプリは作り替えない。既存アプリ側の改修は、実績の取込口に限る

## 3. 動作環境と運用の前提

- **本番**: 担当者PC(Windows)。サーバー専用機はない。クラウドは企業方針で使わない
- **開発**: 開発者PC。担当者と開発者は(現在は同一人物だが)別人として扱う。本番データを開発者PCに置かない
- **利用端末**: 現場のタブレット、管理用のPC。どちらも社内LAN経由でブラウザから担当者PCに接続する
- **既存アプリ**: 担当者1人が担当者PCで使う。実データはローカルSQLite。共有フォルダにはバックアップだけを置く
- **将来**: 全ライン展開時に、社内LANに置く専用ミニPCへ移せる構成にする(パスやポートは設定ファイルに出す)

## 5. ドメインルール

### 5.1 キッティングNo.

形式: `ファイルNo.-回-生産ライン-発行年月日-その日の発行順`

例: `0722-2-S-251014-01`

| 部分 | 例 | 意味 |
| --- | --- | --- |
| ファイルNo. | 0722 | 生産機種 |
| 回 | 2 | 1=1回目、2=2回目 |
| 生産ライン | S | ラインのコード |
| 発行年月日 | 251014 | 2025-10-14(**生産日ではない**) |
| 発行順 | 01 | その日の発行順 |

- 取込時に5つに分解して保存する。計画の識別キーは、既存アプリと同じ **「キッティングNo.+ロットNo.」**
- 回は既存DBの面(production_side)を正とし、キッティングNo.の回と食い違ったら警告する。ラインも同様に実装ライン(mounting_line)を正とする
- 正規表現は例から推定したもの(`^([^-]+)-([12])-([^-]+)-(\d{6})-(\d+)$`)。各部分の桁数は実データで確認する。形式に合わない番号は取り込まずに警告を出す
- **日程だけの変更では番号は変わらない。数量などの内容の変更では番号が振り直される**

### 5.2 計画データの項目

既存アプリの月次DBの `kitting_plan_items`(1行=1計画=1面)から読む。詳細: docs/design/legacy-integration.md

| 本アプリの項目 | 既存DBの列 | 備考 |
| --- | --- | --- |
| キッティングNo. | kitting_list_no | |
| ロットNo. | lot_no | |
| 品名 | board_name | |
| ファイルNo. | setup_file_no | 既存アプリと同じ正規化をかける(下記) |
| ライン | mounting_line | 既存アプリと同じ正規化をかける(下記) |
| 回 | production_side | "1"=1回目、"2"=2回目 |
| 数量 | planned_qty(REAL) | その面の予定生産数。整数でなければ警告 |
| 累計 | cumulative_qty_external | |
| 発注数 | order_qty | |
| 計画開始・終了 | plan_start_datetime / plan_end_datetime | 書式 `2026/07/01 00:00:00`(日本時間として扱う) |
| 納期 | deadline | |
| 削除 | delete_flag | **考慮しない。** 保存するだけで、取消や変化の判定には使わない |
| 状態 | status | 保存するだけ(本アプリの判定には使わない) |
| 想定タクト(takt_sec) | master.db `production_side_master.takt_time`(TEXT) | ファイルNo.・実装ライン・面ごと。中身は小数の数値("30"、"55.72" など)。数値にできない・マスタに無いときは空にして警告。単位は1枚あたりの秒 |

- **正規化**: ファイルNo.と実装ラインは、既存アプリ(models/production_side_master.py)と完全に同じ規則で正規化する(`domain/normalize.py`)。ファイルNo.: NFKC(全角→半角)→前後の空白を除く→数字だけなら文字列のまま4桁にゼロ埋め(`"4"`→`"0004"`、`"00004"`→`"00004"`)、それ以外は大文字。ライン: NFKC→前後の空白を除く→大文字。想定タクトの検索、キッティングNo.のライン記号との比較も、正規化した値どうしで行う
- **削除フラグ**: 業務上の意味が分からず、実データでもすべて0のため考慮しない
- 既存DBの created_at / updated_at は `YYYY-MM-DD HH:MM:SS`(PCのローカル時刻=日本時間)。正とするDBの決定(6.1)に使う

既存DBには actual_start_datetime / actual_end_datetime(実際の開始・終了)の列もある。実績の反映で埋めるかどうかは、実績の取込口の仕様と一緒に決める。

- 数量: この計画で生産する数(既存アプリは実績登録時の数の確認にこの列を使う)
- 累計: これまでに生産した累計(既存アプリの値を正とし、本アプリで足し込まない)
- 発注数: ロット全体の数
- 想定タクトは回ごとに異なる(表と裏で違う)

### 5.3 組(1回目と2回目)

- 組のキー: **ロットNo. + ファイルNo. + 数量**。品名は確認用(食い違ったら警告)
- 1回目か2回目かは、キッティングNo.の回の部分で判断する
- 同じロットを別の日に分けて作ることは多いが、同じ日に同じロット・同じファイルNo.・同じ数量の計画が重なったことはない。万一重なった場合は、発行日と発行順が早いものどうしを組にし、管理画面に警告を出す

### 5.4 回の工程

各回で、次の工程の開始・終了を記録する。段取りと片付けは回ごと(表と裏で別々)に行う。

詳細: docs/design/run-records.md(5.4〜5.8 の実装の判断の理由。冪等性、二重の記録の防止、完了の写し、board の付帯作業の扱いなど)

| 工程 | step_type | 入力 | 必須 |
| --- | --- | --- | --- |
| 段取り | setup | 開始・終了 | ○ |
| N1チェック | n1_check | 開始・終了 | ○ |
| 生産 | production | 開始・終了・生産数(区切りごと) | ○ |
| 初品チェック | first_article | 開始・終了 | ○ |
| X線検査 | xray | 開始・終了 | 省略あり |
| 片付け | cleanup | 開始・終了 | ○ |
| NG数 | (run_inputs: ng_qty) | 数値(回ごと) | |
| 備考 | (run_inputs: remark) | 自由記入 | |

ルール(`services/run_records.py`。違反は 409 と、画面にそのまま出せる日本語の理由):

- **生産の区切り**: 画面は「生産開始」「生産終了(生産数)」を繰り返し押す形にし、区切り番号(seq)は計画×工程ごとに1から自動で振る。2回目以降の区切りを開始するときは、再開理由(理由マスタのうち「生産の再開理由として使える」もの)が必須。1回目の生産とほかの工程では再開理由を受け付けない
- **再開理由の設備**: 2回目以降の生産の開始で、設備が必要な再開理由(マシントラブルなど)を選んだときは、設備(equipment_id)を任意で受け付ける(計画のラインの有効な設備であること)。それ以外の場合は受け付けない。ライン画面用の取得(board)でも返す
- **生産の区切りで入れる数は、良品の数(NGを含まない)。NGは別に入力する**(NG数は下の「NG数だけは…」の入力)。NGの数を引いて入れない。画面の生産終了の入力にも、そのことを書く。この数を、生産数・進捗率・実績の書き出し・日報で使う(取り消した記録は除く)
- 生産の終了は良品数(0以上の整数)が必須。ほかの工程の終了では良品数を受け付けない
- 区切りは記録用紙の欄が3つなので、画面上の目安は3回。**データ上は上限を設けない**
- **工程は繰り返し記録できる**(例: トラブルで別の計画に切り替え、戻ってから段取りをやり直す。seq が2になる)
- 異なる工程どうしは時間が重なってよい(例: 生産中に初品チェック)
- 工程の記録・生産数・備考・完了は、**キッティングNo.(計画のまとまり)の単位**で記録する(ロットNo.を使わない)
- 同じキッティングNo.の同じ工程で、終了していないものがあるのに開始はできない(生産の区切りどうしも重ならない)。終了していないものが無いのに終了はできない。DBにも「終了していない記録はキッティングNo.×工程で1件まで」の一意制約を持たせ、同時の操作でも二重に記録しない
- **NG数だけは、ロットとNGが出た面を選んで入力する**(記録: 入力した画面の計画のキッティングNo.、ロットNo.、面、NG数、入力者、日時)。同じ「キッティングNo.+ロットNo.+面」の入力は最新の値を有効とし、過去の値は履歴として残す
  - 選べる面: 面1の計画では面1だけ。面2の計画では面2と、同じロットNo.・同じファイルNo.の面1の計画が見つかるときの面1(見つからなければ面1は選べない)
  - 面1のNGには、対応する面1の計画のキッティングNo.も記録する(既存アプリに返すときに使う)
- 計画が無ければ 404。取消の計画は開始できない(終了はできる)
- 時刻はサーバーの時計で記録する。記録者の決め方は 5.6
- NG数は行を追加し、最新の値を有効とする(上書きしない)。備考は追加する
- 詳細: docs/design/run-records.md(NGで面を区別する理由、既存アプリの保存の形への変換)
- 計画をまたぐ重なりは基本的にないが、トラブルで今の計画を止めて別の計画を生産することはある。計画の順番の入れ替えもある(最終的に生産がそろえばよい)

API:

| メソッド | パス | 本文 |
| --- | --- | --- |
| GET | `/api/runs/{kitting_no}` | (計画のまとまり1件の状態) |
| POST | `/api/runs/{kitting_no}/steps/{step_type}/start` | request_id、restart_reason_id?、equipment_id?、operator_id? |
| POST | `/api/runs/{kitting_no}/steps/{step_type}/end` | request_id、produced_qty?、operator_id? |
| PUT | `/api/runs/{kitting_no}/ng-qty` | request_id、lot_no、side(NGが出た面)、ng_qty、operator_id? |
| POST | `/api/runs/{kitting_no}/remarks` | request_id、text、operator_id? |

**冪等性**(0-5): すべての操作で request_id を送る。同じ request_id の再送には、最初の応答をそのまま返す(200)。同じ request_id で内容が違えば 409。ルール違反で失敗した操作は記録しないので、同じ request_id で送り直せる(`services/idempotency.py`、表 api_requests)。

**訂正**(`services/run_corrections.py`、共通のルールは `services/correction_rules.py`。違反は 409 と日本語の理由):

- 直せるもの: 工程の記録の開始・終了の時刻、生産の区切りの生産数。記録の**取り消し**(行は消さず、取り消しの印 voided_at・voided_by・void_reason を付ける)。押し忘れた工程の**後からの追加**(工程の種類、開始と終了の時刻、生産なら生産数。後から足した印 added_later を付ける)。NG数と備考は、今までどおり入力し直す(最新の値を有効とし、履歴が残る)
- 取り消した記録は、生産数・進捗・完了・タイムテーブル・工程の状態・「始めた計画か」の判定から外す。画面の履歴には残す。取り消した記録の番号(seq)は使い回さない。取り消していない生産の区切りが無ければ、次の生産の開始は1回目の扱い(再開理由は要らない)
- 理由が必須: 押し間違い(mistake)/ 押し忘れ(forgot)/ 数の入力の誤り(wrong_qty)/ その他(other。内容の記入が必須)。一覧は固定(`domain/corrections.py`)
- 直した人は、ラインの今の担当者(operator_id か worker_id の指定でも可。5.6)
- 時刻: 開始 < 終了、未来の時刻は不可、同じ計画の生産の区切りどうしは重ならない(端が接するのはよい)。終了していない記録は今も続いているとみなし、同じ工程のほかの記録と重ねない。終了していない記録の終了の時刻は直せない(終了のボタンで終える)。時刻はタイムゾーン付きで送る(無ければ 422)
- 現場の画面から直せるのは、開始か終了が「今の稼働日の前後 `corrections.field_margin_hours`(既定12時間。タイムテーブルの表示範囲と同じ48時間)」にある記録だけ。入れる時刻も同じ範囲の中だけ。範囲の外は 409「管理画面から直してください」
- 変更が無い訂正は 409。冪等性(request_id)と書き込みのロックは、ボタン操作と同じ
- 訂正のたびに run_corrections に1行残す(対象、種類、変わった項目ごとの変更前と変更後、理由、記入、直した人、日時、どの画面から)。完了した計画の訂正では、完了の写しを作り直す(5.7)

| メソッド | パス | 本文 |
| --- | --- | --- |
| PATCH | `/api/runs/{kitting_no}/events/{event_id}` | request_id、reason、note?、start_at?、end_at?、produced_qty?、operator_id? / worker_id?(直す項目だけ送る) |
| POST | `/api/runs/{kitting_no}/events/{event_id}/void` | request_id、reason、note?、operator_id? / worker_id? |
| POST | `/api/runs/{kitting_no}/events` | request_id、reason、note?、step_type、start_at、end_at、produced_qty?(生産では必須)、operator_id? / worker_id? |
| GET | `/api/runs/{kitting_no}/corrections` | (その計画の訂正の履歴。新しい順) |

訂正の応答は、訂正の記録(correction)、直したあとの記録(event)、完了しているか(completed)、作り直した完了(completion)。

### 5.5 付帯作業(ライン単位)

計画の合間に起きる、ラインを止める出来事。**計画には結びつけず、ラインに記録する。**

生産の区切りの再開理由と、付帯作業の種類は、共通の理由マスタ(reasons)で持つ(マシントラブルの合計時間を、計画の中か合間かに関係なく集計できるように)。初期データ(マイグレーション 0004):

| 理由 | 区分 | 追加の入力 | 付帯作業 | 再開理由 |
| --- | --- | --- | --- | --- |
| 部品探し | ロス | | ○ | ○ |
| 欠品 | ロス | | ○ | ○ |
| マシントラブル | ロス | 設備を選ぶ(そのラインの設備。必須) | ○ | ○ |
| 立上立会 | ロス以外 | | ○ | |
| 応援・その他 | ロス以外 | | ○ | |
| その他トラブル | ロス | 理由の記入(必須) | ○ | ○ |
| 人員交代 | ロス以外 | | | ○ |
| トラブル停止 | ロス | | | ○ |
| 計画切替 | ロス以外 | | | ○ |

- 理由の列: name、name_vi(ベトナム語の名前。空を許す。7.5)、category(loss=ロス / non_loss=ロス以外)、counts_in_utilization(稼働率に含めるか)、requires_equipment、requires_text、usable_as_line_event、usable_as_restart、active、sort_order
- 開始・終了と、開始した人・終了した人を記録する
- 効率(5.8)は付帯作業の時間を分母に入れない(工程と重なる分は工程の時間から引く)。付帯作業の時間は理由によらず分母に入れない。理由の列 counts_in_utilization と run_completions.utilization は消さずに残すが**使っていない**(管理画面の理由の設定からも隠した)
- 種類はマスタで追加・変更できるようにする(今は開発用のコマンド `python -m app.cli` で一覧だけ。管理画面で作る)
- 生産の再開理由として使うときは、理由の記入は求めない。設備が必要な理由でも、設備は任意(5.4)

ルール(`services/line_events.py`。違反は 409):

- 「付帯作業として使える」理由だけ選べる。設備が必須の理由ならそのラインの設備が必須、記入が必須の理由なら記入が必須
- 同じラインで同じ理由の付帯作業が終了していないのに開始はできない。異なる理由どうしは重なってよい
- 計画を選んでいなくても開始できる。記録者の決め方と冪等性は工程と同じ

API:

| メソッド | パス | 本文 |
| --- | --- | --- |
| POST | `/api/lines/{line_code}/events/start` | request_id、reason_id、equipment_id?、reason_text?、operator_id? |
| POST | `/api/lines/{line_code}/events/{event_id}/end` | request_id、operator_id? |
| PATCH | `/api/lines/{line_code}/events/{event_id}` | 訂正: request_id、reason、note?、start_at?、end_at?、reason_id?、equipment_id?、reason_text?(直す項目だけ) |
| POST | `/api/lines/{line_code}/events/{event_id}/void` | 取り消し: request_id、reason、note? |
| GET | `/api/lines/{line_code}/corrections?date=YYYY-MM-DD` | 付帯作業の訂正の履歴(付帯作業の開始がその稼働日にあるもの。新しい順。省略すると今の稼働日) |

付帯作業の訂正(`services/line_event_corrections.py`): 開始・終了の時刻、理由(設備・記入が必要な理由ならそれも。開始のときと同じルール)を直す、または取り消す。理由・直した人・範囲・冪等性・時刻のルールは工程の記録の訂正(5.4)と同じ。同じ理由の付帯作業のうち、終了していない記録とは重ねない(終了したものどうしは重なってよい)。取り消した付帯作業は、「同じ理由が終了していない」の判定とタイムテーブルから外す

### 5.6 誰がやったか

- すべての記録に、開始した人と終了した人を別々に持つ(人員交代で変わるため)
- ラインごとに「今の担当者」を設定し、ボタン操作の記録に自動で付ける。担当者は始業時と人員交代時に切り替える。1回の操作だけ別の人にすることもできる
- 実装(`services/line_operators.py`): 表 line_operators に履歴を持つ。交代すると前の行に end_at を入れ、新しい行を足す(今の担当者はラインに1人。すでに同じ人なら何も変えない)
- 記録者 = 本文の operator_id(本アプリの中の番号)か worker_id(作業者ID)のどちらか。指定が無ければラインの今の担当者。どちらも無ければ 409「担当者が設定されていません」。実績の訂正で「直した人」も同じ決め方(5.4)
- **作業者は既存アプリの master.db の workers から読み込む**(計画の同期のたびに。読み取り専用。計画の表が無いなどで計画の同期がエラーになっても、workers が読めれば作業者は読み込む)。名前・役割(admin / operator)・有効/無効を既存アプリに合わせ、既存アプリから見えなくなった作業者は消さずに無効にする(過去の記録が参照しているため)。作業者IDは既存アプリの表記のまま持ち、全角・半角と大文字・小文字の違いを無視して比べる(`domain/worker_id.py`)。正規化すると重なるIDは、片方を取り込まずに警告を出す
- legacy_app_dir が設定されていない環境(開発用)だけ、開発用コマンドで作業者を足せる(`python -m app.cli operators add <名前> --id <作業者ID>`。source=local)
- 担当者は**作業者IDで呼び出す**(PIN は付けない。11. 未確定事項)。画面では作業者IDの入力欄を一番上に置き、Enter(または「呼び出し」)でIDと名前を表示して確かめてから決める。入力欄はタブレットの文字キーボードが出る形で、将来の社員証のバーコードリーダー(文字の入力 + Enter)でも動く。名前の一覧(名前順。IDも並べる)から選ぶ方法も補助として残す
- 同じ名前の人がいても区別できるよう、画面の上部や記録の表示では名前の横に作業者IDも出す

| メソッド | パス | 説明 |
| --- | --- | --- |
| GET | `/api/lines/{line_code}/operator` | 今の担当者(未設定なら null) |
| PUT | `/api/lines/{line_code}/operator` | 交代する(本文: request_id、operator_id か worker_id) |
| GET | `/api/operators/lookup?worker_id=` | 作業者IDで、有効な作業者を呼び出す(無ければ 404「作業者IDが見つかりません」) |

ラインの記号は、既存アプリと同じ規則で正規化してから探す(`s` → `S`)。ラインは計画の同期で新しい記号を見つけたら自動で登録する(名前は「<記号>ライン」)。

### 5.7 完了と実績の反映

- **片付け終了 = その回の完了。** このとき次を行う
  - その時点の計画数・想定タクト・丁取り数とその status を、実績と一緒に保存する(後で計画や丁取りが変わっても、過去の効率や日報が変わらないように。5.8)
- **製品の最終の回が完了したら、既存アプリへ実績を反映する**
  - 製品の完成数 = 最終の回の生産数(区切りの合計)。1回目と2回目を足さない
  - NG数は回ごとに分けて返す(既存アプリが回ごとに持っている)
- 完了後の誤りは、管理者が訂正し(訂正履歴を残す)、区分「訂正」で再出力する
- 実装済み(run_completions。キッティングNo.の単位): 片付けの終了で1件作る。生産数=区切りの合計、計画数(ロットの数量の合計)と想定タクトの写しに加えて、丁取り数とその status(`teitori_snapshot`・`teitori_status_snapshot`)、その時点のロットの一覧(ロットNo.・基板名・数量)と、ロットと面ごとの最新のNG数も写す。片付けをやり直して終了したらもう1件作り、最新のものを有効とする。完了後も工程の記録は受け付ける
- **訂正と完了**(`services/completions.py`): 完了した計画の工程の記録を直した・取り消した・足したときは、完了の写しを作り直す(新しい行を足し、kind=correction と元になった訂正 correction_id を記録する。最新の有効な行を正とする)。完了の時刻は片付けの終了の時刻。生産数とNG数は今の値、計画数・想定タクト・丁取り数・ロットの一覧は前の完了の写しを引き継ぐ。押し忘れた片付けを後から足したときも完了になる
- 有効な完了 = 完了にした片付けが取り消されていない行。**片付けの終了を取り消すと**、ほかに終了した片付けが残っていればそれで作り直し、無ければ完了でない状態に戻る
- 既存アプリはNGを「キッティングNo.+ロットNo.+面」で、面1 = 面1の欄 + 面2の欄 の形で持つ。本アプリはその面だけの値を書き出し、足し込みは既存アプリがする(5.9)
- ライン画面用の取得: `GET /api/lines/{line_code}/board?date=YYYY-MM-DD`(計画ごとの工程の記録・生産数の合計・最新のNG数・完了・進捗率(生産中のみ)と、その日の付帯作業、今の担当者、その稼働日の効率)、`GET /api/masters?line_code=`(有効なマスタ)

### 5.8 効率と進捗率

計算は `services/metrics.py` だけで行い、ライン画面のバー・日報・区間の CSV は同じ値になる。式・決め・例・丁取りの取り込みは [docs/design/metrics.md](design/metrics.md)。

- **効率(%) = Σ(目標タクト × 良品台数 ÷ 丁取り数) ÷ Σ(実所要時間) × 100**(以前の「稼働率」はこれに置き換えた)
  - 目標タクト: 想定タクト(`plans.takt_sec`。1枚あたりの秒)。良品台数: 生産の区切りの数(NGを含まない)を丁取り数で割って枚数にする(切り上げない)
  - 実所要時間: すべての工程の記録の時間。付帯作業の時間は分母に入れない(重なる分は工程の時間から引く)。取り消した記録は入れず、作業中は今まで数える
  - 対象はその稼働日(8:15 始まり)に工程の記録がある計画。境目をまたぐ記録は時間を分け、良品数は区切りが終わった稼働日に数える。計画どうしの重なりは統合せず、計画(キッティングNo.)ごとに足す
  - 目標タクトか丁取り数が無い計画は、分子と分母の両方から外す(1を仮定しない)。外した件数と理由を画面と日報に出す。ロットで目標タクトか丁取りが違えば警告し、最初のロットの値を使う
  - 完了した計画は完了の写しの値、作業中の計画は今の値を使う
- **進捗率(%) = 工程の記録の時間の合計 ÷ 計画の時間(計画終了 − 計画開始) × 100**。生産中(最初の工程を始め、片付けが終わっていない)の計画だけに出す。100%を超えてもそのまま出し、計画の時間が無い・0以下なら「—」。以前の「生産数 ÷ 計画数」は置き換えた。既存アプリの完成判定は変えない
- 工程・区切り・付帯作業の開始と終了、生産数、想定タクト、丁取り数を漏れなく記録する
- ロット全体の進み具合は、既存アプリの累計と発注数を参照して表示する

### 5.9 実績の書き出し(既存アプリに戻すための CSV)

管理画面の「実績の書き出し」から、片付けが終わった計画の実績を CSV に書き出す。既存アプリのDBには書かない(取り込むのは既存アプリの取込口)。詳細: docs/design/actuals-export.md

- 絞り込み: 期間(完了日の稼働日)、ライン。対象は片付けが終わった計画(有効な完了がある計画のまとまり)だけ
- **1行 = キッティングNo.+ロットNo.**
  - 面1と面2の計画は、**ロットNo. + キッティングNo.から「回」を除いた部分(ファイルNo.・ライン・発行年月日・発行順)** でひも付ける(キー H。有効な計画だけ)。この部分は面ごとに一意なので、取り違えは起きない
  - つながる面2がある面1は、面2の (キッティングNo., ロットNo.) の行にまとめる(NG面1 もそこへ)。面1の行は出さない(製品の完成数は最終の回の生産数のため。5.7)
  - 面1の行を単独で出すのは、同じ (ロットNo., ファイルNo.) に面2の計画が1件も無いときだけ
  - 面2の計画があるのに H でつながらない面1は、書き出しの対象から外し、**「ひも付けの確認」** に出す。管理者が面2の計画を選んで確定する(「つながない(面1は書き出さない)」も選べる)。候補は同じ (ロットNo., ファイルNo.) の面2の計画で、発行日が最も近いものを初期の選択にする。確定した組は H でつながった組と同じに扱う。確定は表 side_links に残し、やり直しは新しい行で上書きする(履歴は消さない)。1つの面2の計画につながる面1は1つだけ
  - 未確定が残っているときは、書き出しの画面の上に件数を出す(書き出し自体は止めない)
  - つながる面1が無い面2の行は単独で出す。NG面1 は0とし、行に注意書きを出す
- 値
  - 生産数: **良品の数(NGを含まない)**。その計画(キッティングNo.)の累計(取り消した記録は除く)。見出しは「生産数(累計)」のまま。日ごとの増分ではない
  - NG面1・NG面2: その面だけの値(足し込みは既存アプリがする)。空は0。NGが出た面の計画への最新の入力
  - 日付: 完了日(片付けの終了の稼働日)。YYYY-MM-DD
  - 書式版: 2(列を変えたら上げる。1 は12列、2 は「面1のキッティングNo.」を足した13列)
  - 書き出し日時: YYYY-MM-DD HH:MM:SS(日本時間、タイムゾーンなし)に固定する
  - 面1のキッティングNo.: 面2の行で、つながる面1(キー H でつながった組、または管理者が確定した組)があるときは、その面1のキッティングNo.(NG面1 が 0 でも入れる)。それ以外(面1の行、つながる面1が無い面2の行)は空。既存アプリが面1の計画を推測せずに使えるようにするため
  - 担当者ID: 完了にした片付けを終えた人の作業者ID。既存アプリの workers の worker_id と同じもの(表記のまま。無ければ警告を付けて外す)
  - 元のDB(フォルダ名): そのロットの正のDBのフォルダ名(`<legacy_app_dir>\db\<フォルダ名>\inventory.db` の `<フォルダ名>`。6.1)
  - Excel で開いて保存した CSV は、ロットNo.などが壊れるので、保存せずに取り込む(画面にも出す)
- **生産数のロットへの割り振り**: キッティングNo.ごとの生産数の合計を、ロットの並び順(ロットNo.の順)に、各ロットの計画数まで入れ、余りは最後のロットに入れる。ロットが1つなら全部をそのロットに入れる(`domain/allocation.py`)。画面で行ごとに数を直せる。直したあと、キッティングNo.ごとのロットの合計(一覧に出さない面1のロットの分も含む)が元の合計と一致しないと書き出せない(409 と日本語の理由)。直した数は保存しない
- CSV: BOM 付きの UTF-8、改行は CRLF。見出しの列は次の順: 書式版、書き出し日時、元のDB(フォルダ名)、キッティングNo.、ロットNo.、ファイルNo.、面(1か2)、日付、生産数(累計)、NG面1、NG面2、担当者ID、面1のキッティングNo.(最後に足した列)
- 保存先: `exchange_dir` の `actuals` フォルダ(`actuals_<年月日>_<時分秒>_<書き出しの番号>.csv`。一時ファイルに書いてから改名する)。画面からもダウンロードできる
- 書き出しの履歴(いつ・誰が・何行・ファイル名。表 actuals_exports)を残す。書き出しても実績の記録は変えないので、同じ内容を何回書き出しても、こちらの記録は変わらない
- 想定タクトは既存アプリの production_side_master.takt_time(1枚あたりの秒)

## 6. 既存アプリとの連携

### 6.1 計画の取得(既存 → 本アプリ)

- 既存アプリのSQLiteを**読み取り専用**で開き(SQLiteのURIで `mode=ro`)、一定間隔(既定1分、設定で変更可)で計画を読む。読み取りは短く終える
- 既存DBの構造に依存する処理は `integration/legacy/`(入口は `integration/legacy_plans.py`)に閉じ込める
- 詳細: docs/design/legacy-integration.md(既存アプリの調査結果、正とするDBの決め方と取消にしない条件の理由)
- 差分は**自動で反映**する(計画は頻繁に変わるため、人の確認は挟まない)

**読むDB**(設定は既存アプリのフォルダ `paths.legacy_app_dir` だけ):

| ファイル | 扱い |
| --- | --- |
| `<既存アプリのフォルダ>\db\<フォルダ名>\inventory.db` | 月次DB(フォルダ名は自由)。**すべて読む**。ただし、ファイルの更新日時が `sync.legacy_db_max_age_days`(既定120日)より古いものは読まない |
| `<既存アプリのフォルダ>\db\inventory.db` | 「未選択」を表す既定DB。読まない |
| `<既存アプリのフォルダ>\db\master.db` | 共通マスタ(想定タクト) |

- どのDBも journal_mode=delete(WALではない)なので、読み取り中は既存アプリの書き込みを待たせる(既存アプリの待ち時間は30秒)。**DBごとに接続を開き、有効な計画とロットごとの最終書き込み時刻を1つの読み取りで取って、すぐ閉じる**
- 同期の記録(plan_sync_runs)に、その回に読んだDBの一覧と、DBごとの計画の件数を残す

**ロットごとに正とするDB**(`services/plan_source.py`):

実績は計画(キッティングNo.+ロットNo.)に付けるものなので、計画がどの月次DBにあるかにはとらわれない。棚卸の期間が重なり、既存アプリでDBを行き来することがよくあるため、同じロットが複数のDBにあるときは**ロットごとに、最後に書き込まれたDBを正とする**。

- ロットの最終書き込み時刻 = そのDBのそのロットの全行(無効な行も含む)の MAX(updated_at)
  - 既存アプリは、新しい版を作ると古い行の is_active と updated_at を更新し、新しい行は INSERT 時刻になる。削除(ソフト)も updated_at を更新する。前月からの引き継ぎ(ロット単位)でコピーした行は、コピーした時刻になる。実績の登録などでは計画の行は書き換えない
  - バックアップから戻したDBは元の時刻のままなので、正にならない
- 同じ時刻のときは、DBファイルの更新日時が新しいほうを正とする。内容が違えば警告を出す
- 同期で使う計画 = 各ロットについて、正とするDBの有効な計画だけ。正とするDBにそのロットの有効な行が無ければ(削除(ソフト)など)、そのロットの計画は「消えた」扱い
- 警告は、正とするDBの行のものだけを出す。どのDBの行か分かるよう、警告の先頭にDBのフォルダ名を付ける

**取消にしない条件**: 計画が正とするDBに無くても、次の場合は取消にせず、値も状態も変えない。

| 状況 | 扱い |
| --- | --- |
| 月次DBが1つでも読めなかった | 何も反映せず、同期の記録を error にする(どのDBが正か決められないため) |
| ロットがどの月次DBにも見当たらない(古くなって読まなくなった、など) | 取消にしない。警告を出す |
| 計画終了が今日の 0:00 より前 | 取消にしない(古い月次DBが読む対象から外れても、過去の計画を残すため) |
| 形式エラーで読めなかった行の計画 | 取消にしない(既存DBに行は残っているとみなす) |

取消にするのは、**ロットがどこかの月次DBにあり、かつ正とするDBにその計画が無いとき**だけ。

既存アプリの計画の持ち方(「版」方式):

- 計画を変えると、前の行を `is_active = 0` にして、`version` を1つ上げた新しい行を足す。行は削除しない
- 「キッティングNo.+ロットNo.」で有効な行は1件まで(部分ユニークインデックス)
- **内容が同じでも、取り込み直すと版が上がる。** したがって本アプリは `version` では変化を判定せず、**内容を比べて**判定する(`services/plan_diff.py`)
- 本アプリが読むのは `is_active = 1` の行だけ。キッティングNo.が空の保留行(pending_kitting_plan_items)は読まない

| 状況 | 扱い |
| --- | --- |
| 実績がない計画の変更・削除 | そのまま反映する |
| 実績がある計画の日程・数量の変更 | 計画の値を更新し、実績はそのまま |
| 実績がある計画が既存側で消えた | 実績は消さず、状態を「取消(実績あり)」にして警告する |
| 番号の振り直し(内容変更) | 下の「引き継ぎ」を行う |

**引き継ぎ**: 実績のある計画が消え、同じ同期でロットNo.、ファイルNo.、回が同じ新しい計画が現れたら、引き継ぎの候補とする。候補が1つなら実績を自動で新しい番号へ移し、複数なら管理画面で選んでもらう。元の番号と引き継ぎの記録は履歴に残す。

**安全装置**: 1回の同期で取消になる計画が多すぎるとき(既定は10件以上 かつ 分母の30%以上。設定で変更可)は、既存アプリのフォルダの設定間違いなどを疑い、何も反映せずに同期の記録を「反映を保留(guarded)」にする。

- 分子: この同期で取消になる計画の件数(上の「取消にしない条件」に当たるものは含まない)
- 分母: 有効な計画のうち、**計画終了が今日の 0:00 以降(または計画終了が空)のもの**。過去の計画は取消の対象にならないので、分母に入れると安全装置が効きにくくなるため除く

### 6.2 実績の反映(本アプリ → 既存)

- 連携フォルダ(`exchange_dir\actuals`)にCSVを書き出し、既存アプリに新設する取込口で取り込む。書き出しは管理画面から行う(5.9)
- 書き手は一時ファイル名(`.tmp`)で書き終えてから `.csv` に改名する。読み手は `.csv` だけを読む
- ファイル名: `actuals_YYYYMMDD_HHMMSS_<書き出しの番号>.csv`。書き出しの履歴(actuals_exports)に、いつ・誰が・何行・ファイル名と CSV の中身を残す
- 文字コード(BOM 付きの UTF-8)、列、実績日(=完了日)は 5.9 のとおり。値は累計なので、同じ行を何回取り込んでも上書きすれば同じ結果になる。既存アプリの取込口の作りは未定(「11. 未確定事項」)

## 7. 画面

### 7.1 現場画面(タブレット)

1. **ダッシュボード**: 生産ラインを選ぶ
2. **ライン画面**: 3カラム構成

```
┌──────────────────────────────────────────────┐
│ 上部: 今日の効率 / 生産中の計画の進捗率 / 今の担当者 │
├────────┬──────────────────────┬───────────────┤
│ 左     │ 中央                 │ 右             │
│ メニュー │ タイムテーブル(縦軸が時刻) │ 選んだ計画の     │
│        │ ・計画の枠(最新の順番)    │ 工程ボタンと入力欄 │
│        │ ・実績(押された時刻)      │ ・付帯作業のボタン │
│        │ ・付帯作業のブロック      │               │
└────────┴──────────────────────┴───────────────┘
```

- タイムテーブルで計画をクリックすると、右カラムにその回の工程ボタンが表示される
- 計画の枠は最新の計画の順番で、実績は実際にボタンが押された時刻で描く(順番が入れ替わっても実績は動かない)
- 付帯作業のボタンは、計画を選んでいなくても押せる
- **表示範囲**: 稼働日の始まりの12時間前から、終わりの12時間後までの48時間(例: 稼働日 10/21 → 10/20 20:15〜10/22 20:15)。タイムテーブルの縦軸はこの48時間で、稼働日の境目(8:15)に線と日付を出す。開いたときは今の時刻のあたりまで自動でスクロールし、今の時刻の線はサーバーの時刻との差を補正して引く。表示範囲からはみ出す計画の枠は端で切り、切れていることが分かる印を付ける
- 画面は**キッティングNo.(計画のまとまり)の単位**。タイムテーブルの枠はキッティングNo.ごとに1つで、キッティングNo.・ロットの数(例: 3ロット)・計画数の合計を出す。右のパネルの見出しにロットの一覧(ロットNo.、基板名、数量、面ごとのNG数)を出す(多いときはパネルの中でスクロール)。NGは、ロットを選ぶ → 面を選ぶ(選べない面は押せない) → テンキーで数を入れる。入力済みのNGは一覧で見られる
- **ライン画面に出す計画**(有効な計画のまとまりのうち、次のどれか)
  1. 計画開始〜終了が表示範囲と重なる
  2. 表示範囲の中に実績の記録がある(先行して始めた計画)
  3. 作業を始めたが、片付けが終わっていない(日付は問わない。遅れている計画)
  - ただし、計画終了が過ぎたのに未着手の計画は出さない(検索で選ぶ)
- 上部のバーは、今日の稼働日の**効率**(外した計画があれば件数)と、**生産中の計画ごとの進捗率**を出す(5.8。以前の「ラインの進捗率」は廃止)
- **計画の検索**: 左のカラムの上の検索欄で、キッティングNo.・ロットNo.・基板名の一部で探す(`GET /api/plans/search?q=&line_code=`。英字の大文字・小文字と全角・半角の違いは無視。有効な計画のみ、計画開始が今に近い順に最大20件)。ロットNo.や基板名で当たっても、そのキッティングNo.のまとまりを返し、当たったところ(ロットNo.・基板名)を出す。結果を押すとその計画を選ぶ。キッティングNo.が完全に一致する計画が1件だけなら、Enter でそのまま選ぶ(将来のバーコードリーダーのため)。選んだ計画が表示範囲の外なら「表示範囲外の計画です(計画: 10/18 9:00〜)」と出す
- 担当者が未設定のまま記録のボタンを押したら、サーバーに送らず、先に担当者を選ぶ画面を出す
- **実績の訂正**(5.4、5.5): 右のパネルの工程の行に「直す」(記録が無い工程は押せない)。押すと訂正の画面: 記録を選ぶ(複数あるとき) → 開始・終了の時刻(±1時間・±10分・±1分の大きなボタン。今より後にはできない)、生産数(テンキー) → 理由(その他は記入) → 「訂正を記録」。「この記録を取り消す」で取り消し。右のパネルに「押し忘れの追加」(工程を選び、開始と終了の時刻と生産数を入れる。理由の既定は押し忘れ)と「訂正の履歴」(記録の一覧と訂正の履歴。取り消した記録は取り消し線)。付帯作業のパネルに「付帯作業を直す」と「訂正の履歴」。取り消した記録はタイムテーブルに出さない。生産の区切りの「何回目」は、取り消していない区切りを開始の順に数える
- 詳細: docs/design/line-screen.md(実装した画面の作り、ボタン操作の送り方、稼働日と表示範囲の理由、タブレット向けの決まり)

### 7.2 管理画面(PC)

- 日報: ラインの実績を24時間のガントチャートで表示する
- 計画の同期状況と警告(取消(実績あり)、引き継ぎの候補、組の食い違い、再印刷が必要)
- 実績の訂正(訂正履歴を残す)と再出力
- マスタ: ライン、設備、理由(停止理由・付帯作業の種類)、作業者、管理者
- 記録用紙の印刷

実装済み(1回目: ログインとマスタ。詳細: docs/design/admin.md):

- 管理画面に入れるのは、作業者(operators)のうち役割が admin で有効な人だけ。既存アプリで admin でなくなった・無効になったら、ログイン中でも次の操作で締め出す
- ログインは作業者IDとパスワード。パスワードは本アプリで持ち(ハッシュ。8文字以上)、最初の設定とリセットは開発用コマンド(`admin set-password`)、自分での変更は管理画面で行う。同じ作業者IDで続けて5回間違えたら5分ログインできない。失敗の理由は区別しない
- 操作が無い30分、またはログインから12時間でログインが切れる(config.toml の `[admin]` で変えられる)
- マスタ: 設備と理由の追加・変更・無効化、ラインの名前・並び順の変更と無効化、作業者の一覧(見るだけ)。行は消さず、変更はすべて audit_log に残す。無効にした理由・設備は現場の画面で選べなくなるが、過去の記録の表示は変わらない
- 管理画面は日本語だけ。PC(幅 1280px 以上)で使う。ライン選択の画面の隅から入る
- **アクセス制限**(「アクセス制限」ページ。詳細: docs/design/security.md): 登録したIPアドレス(1台と CIDR、IPv6 も)だけが画面・API・静的ファイルを使える。現場用と管理画面用の2つの一覧。一覧、追加、無効化(履歴は残す)、「今の接続元を追加」、今の接続元が許可されているかの表示。今の接続元が外れる変更は受け付けない。緊急用に `GenbaCli.exe ip list / add / remove / disable-all`

実装済み(2回目の一部: 日報と区間の CSV。詳細: docs/design/reports.md):

- **区間の CSV**: 1行 = 1つの区間。見出しは日本語、BOM 付きの UTF-8、改行は CRLF(Excel でそのまま開ける)。ファイル名は `intervals_<始め>_<終わり>_<ライン または all>.csv`。期間の上限は config.toml の `[reports] max_days`(既定93日。超えたら 409)

### 7.3 記録用紙

- A4縦1枚に、上半分が1回目、下半分が2回目

- 複数の製品を選び、1製品1ページで一度に印刷できるようにする
- 印刷後に計画が変わったものは、管理画面に「再印刷が必要」と表示する(印刷時の計画の値を記録して比較する)
- 試行中は一部の手書きを残す。**Webで入力する項目はWebの値を正とする**

### 7.5 表示言語の切り替え

- 現場画面は、日本語とベトナム語を切り替えられる。切り替えのボタン(「日本語 / Tiếng Việt」)は、ライン選択の画面と、ライン画面の上部に置く
- 選んだ言語は、その端末に記憶する(最初は日本語)
- 画面の文言は辞書(`frontend/src/i18n/ja.ts`。ベトナム語は `vi.ts`)に集め、画面のファイルに直接書かない。用語は日本語の辞書で「2. 用語集」に従う
- 訳さないもの: サーバーが返すエラーの文(409 / 404 / 503 の理由。日本語のまま出す)、計画の内容(キッティングNo.、ロットNo.、基板名など)、作業者の名前
- 理由と設備の名前は、マスタのベトナム語の名前(name_vi)を出す。空なら日本語の名前を出す。初期データの理由には、ベトナム語の名前を入れてある(マイグレーション 0009)
- ラインの名前は、計画の同期で自動で付けた形(「<記号>ライン」)のままなら選んだ言語の形で出す(ベトナム語は「Chuyền S」)。人が名前を変えていたら、その名前をそのまま出す
- 日付と時刻は、どちらの言語でも同じ形(24時間表記、日本時間)
- ベトナム語の訳はレビュー役が用意する(初版は 2026-10-21 に取り込み済み)。新しく足した文言で訳がまだのものは「(未翻訳)」と日本語の文を出す
- 詳細: docs/design/i18n.md(仕組み、キーの付け方、文言を足すときの手順)

## 9. 非機能要件

詳細: docs/design/db-writes.md(書き込みのロックの背景とテスト)、docs/design/security.md(セキュリティの調査の結果と、直す順番)

| 項目 | 方針 |
| --- | --- |
| 同時アクセス | uvicornは1プロセス。SQLiteはWAL。端末数台を想定 |
| 書き込みのロック | SQLite は古い読み取りにもとづく書き込みを拒否する(busy_timeout があっても即座に database is locked になる)ため、本アプリのDBに書き込む処理(ボタン操作、計画の同期、開発用コマンド)は、処理の最初に書き込みのロックを取る(BEGIN IMMEDIATE)。あわせて、同じプロセス内の書き込みは1つのロックで1つずつ行う(`app/db/session.py` の `write_transaction`)。計画の同期は、既存DBの読み取りと正とするDBの決定をロックの外で行い、本アプリのDBに反映する部分だけをロックする。それでもロックが取れなかったとき(ほかのプロセスが書き込み中など)は 503「他の処理と重なったため、記録できませんでした。もう一度押してください」を返し、冪等性の記録(api_requests)には残さない(同じ request_id で送り直せば記録される) |
| 認証(現場) | 現場端末はライン単位で使い、記録者は「今の担当者」で特定する(PINの要否は未確定) |
| 認証(管理) | 作業者IDとパスワード(標準ライブラリの scrypt(n=2^17)のハッシュで保存。8文字以上)。セッションは Cookie(HttpOnly、SameSite=Strict。社内LANの HTTP なので Secure は付けない)。操作が無い30分・最長12時間で切れる。続けて5回間違えたら5分ログインできない(同じ接続元からは、作業者IDを問わず20回で5分)。パスワードを変えたら、その人のほかのセッションは無効。データを変える要求には X-Genba-Admin ヘッダーが要る(詳細: docs/design/admin.md) |
| アクセス制限 | 登録したIPアドレスだけ、画面・API・静的ファイルを使える(許可しないときは 403 と日本語の画面)。現場用の一覧が空なら制限しない(今までどおり)。管理画面用の一覧が空なら現場用と同じ。127.0.0.1 と ::1 は常に許可。判定は TCP 接続の相手のアドレスだけで、X-Forwarded-For などは信用しない。拒否は1分に1回までログに残し、起動のログに有効かと件数を出す。一覧を一度も読めないときは制限する側に倒す(127.0.0.1 と ::1 以外は 403)。管理画面で一覧が空になる変更は確認のダイアログを出す。開発サーバー(Vite の 5173)は、サーバーから見ると 127.0.0.1 なので制限できない(本番の 8000 番に直接つなぐときだけ効く)。ファイアウォールの `-RemoteAddress` と併用する二重の守り(詳細: docs/design/security.md) |
| HTTPS | フェーズ1は不要(カメラもPWAも使わないため)。必要になったら社内用の証明書を導入する |
| 時刻 | サーバーの時刻で記録する。担当者PCのWindows時刻同期を有効にする |
| バックアップ | SQLiteのバックアップ機能(`backup()`)で、起動時(DBの構造の更新の前)と毎日決まった時刻(既定 12:30)に、config.toml の backup_dir(共有フォルダ)へ保存する。起動中のファイルコピーはしない。世代は既定30で、古い順に消す(本アプリが作ったファイルだけ)。保存できなくてもアプリは止めず、警告をログに出す(`services/backup.py`。詳細: docs/design/packaging.md) |
| ログ | アプリのログはファイル(`logs\genba.log`)に日ごとに分けて保存する(90日分。`app/server.py`) |
| 障害時 | 担当者PCが止まっている間、現場は紙に記録し、復旧後に管理者が代理入力する(入力者と入力日時を残す) |
| 常時稼働 | タスクスケジューラ(またはWindowsサービス)で自動起動。稼働時間中はスリープ無効。IPアドレス固定。ファイアウォールはアプリのポートだけ許可 |

## 10. 開発・配布・運用

詳細: docs/design/packaging.md(ビルドの中身、担当者PCで使うスクリプト、初めて置くとき・更新するときの手順)

担当者PCのフォルダ構成:

```
C:\GenbaApp\         基準のフォルダ(GENBA_HOME。exe の2つ上。環境変数で変えられる)
  app\v1.0.0\        実行ファイル(GenbaApp.exe。版ごとにフォルダを分ける)
  data\genba.db      本番DB
  data\config.toml   ポート、既存アプリのフォルダ、連携フォルダ、バックアップ先、同期間隔、バックアップの時刻と世代
  exchange\          連携フォルダ
  logs\              ログ(日ごと)
```

- exe は `<基準>\data\config.toml` を読み、config.toml の相対パスは基準のフォルダから見た位置にする(開発中は起動したフォルダが基準)
- exe では、画面の確認用の時計(GENBA_CLOCK_START / GENBA_TEST_MODE)は常に無効
- exe はウィンドウを出さない形が標準(確認用にウィンドウを出す形も作れる)。起動の失敗(設定の誤り、ポートの使用中など)は理由をログのファイルに残して終了する

ビルド(開発者PC): `packaging\build.ps1` を実行する。画面のビルド → テスト(pytest・vitest)→ PyInstaller(フォルダ形式)→ `packaging\dist\v<版>\` と `GenbaApp-v<版>.zip`。版は `backend/app/__init__.py` の `__version__`

自動起動とファイアウォール(担当者PC、管理者権限): `packaging\install-autostart.ps1`(タスクスケジューラ。PCの起動時に、専用のアカウント(-User 必須。SYSTEM・Administrator は断る)で「ログオンしているかどうかにかかわらず実行する」形で起動。ウィンドウは出ない)と `packaging\firewall-allow.ps1`(アプリのポートだけ、相手を絞って受信を許可。-RemoteAddress)。解除は `uninstall-autostart.ps1`、`firewall-remove.ps1`

更新(担当者PC): 停止 → 新しい版のフォルダを置く(旧版は残す)→ 新しい版で自動起動を登録し直す(パスワードを入力する)→ 起動(起動時にバックアップとAlembicを自動実行)→ 稼働確認の画面(/api/health)で確認。問題があれば旧版と更新前のバックアップ(`*_startup.db`)に戻す。
