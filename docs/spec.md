# 現場実績入力・稼働率可視化Webアプリ 開発指針

- 版: 0.2(2026-10-20 既存アプリの計画テーブルの調査結果を反映)
- 位置づけ: このアプリを作るときの**唯一の基準**。企画書・アーキテクチャ設計書(初版)と食い違う場合は、この文書を優先する
- 読み手: 開発者と、開発を手伝うAIアシスタント

---

## 0. AIアシスタントへの指示(必ず守ること)

1. **既存の生産管理アプリのDBには絶対に書き込まない。** 読み取りは「計画の取得」モジュールからだけ行い、読み取り専用で開く
2. **時刻はすべてサーバーで記録する。** ブラウザやタブレットの時計を記録に使わない
3. **実績は物理削除しない。** 誤りは訂正履歴(audit_log)を残して直し、取り消しは状態で表す
4. **権限はすべてのAPIでサーバー側が検査する。** 画面の表示制御だけに頼らない
5. **ボタン操作は冪等にする。** 端末は操作ごとに一意のリクエストIDを送り、同じIDの再送は1件として扱う
6. **「11. 未確定事項」に載っている内容は勝手に決めない。** 仮置きで実装する場合は、コードに `TODO(要確認): <項目名>` を残す
7. 動作環境はWindowsの1台のPCで、**1プロセスで動かす前提**。クラウドや外部サービスは使わない
8. 依存ライブラリを追加するときは、理由とライセンスを書く。**GPL・AGPLのライブラリは使わない**
9. 画面の文言は日本語。用語は「2. 用語集」に従う
10. 既存アプリの仕様が分からないところは推測で埋めず、質問する

---

## 1. 目的と範囲

現場がタブレットのボタンで作業の開始・終了・数量を入力し、管理者がラインの計画と実績、進捗率、稼働率をリアルタイムに見られるようにする。実績は既存の生産管理アプリへ戻し、計画と実績が一致した状態を保つ。

- 試行は1ラインで行う。後に全ラインへ展開する
- 既存アプリは作り替えない。既存アプリ側の改修は、実績の取込口に限る

## 2. 用語集

| 用語 | 意味 |
| --- | --- |
| 既存アプリ | 担当者が使っている生産管理アプリ(デスクトップアプリ、担当者PCのローカルSQLite) |
| 製品 / ロット | 既存アプリの管理単位。ロットNo.は製品に1つ。1つのロットに複数の機種(ファイルNo.)が含まれることがある |
| ファイルNo. | 生産機種を表す番号。同じファイルNo.でも品名が異なることがある(中身は同じ) |
| 計画 | 計画データの1行。キッティングNo.で識別する。**計画1行=1回** |
| 回 | 1回目(表)または2回目(裏)。製品によっては1回目だけのこともある |
| 組 | 同じ製品の1回目の計画と2回目の計画のペア |
| 工程 | 1回の中で行う作業。段取り、N1チェック、生産、初品チェック、X線検査、片付け |
| 区切り | 1回の生産が、人員交代やトラブル停止で分かれたときの各区間(生産1・2・3) |
| 付帯作業 | 計画の合間に起きる、ライン単位の出来事(部品探し、欠品、マシントラブルなど) |
| 完了 | その回の片付けが終了した状態 |
| 引き継ぎ | 計画の内容変更でキッティングNo.が振り直されたとき、実績を新しい番号へ移すこと |
| 担当者PC | 既存アプリと本アプリの本番が動くWindows PC |

## 3. 動作環境と運用の前提

- **本番**: 担当者PC(Windows)。サーバー専用機はない。クラウドは企業方針で使わない
- **開発**: 開発者PC。担当者と開発者は(現在は同一人物だが)別人として扱う。本番データを開発者PCに置かない
- **利用端末**: 現場のタブレット、管理用のPC。どちらも社内LAN経由でブラウザから担当者PCに接続する
- **既存アプリ**: 担当者1人が担当者PCで使う。実データはローカルSQLite。共有フォルダにはバックアップだけを置く
- **将来**: 全ライン展開時に、社内LANに置く専用ミニPCへ移せる構成にする(パスやポートは設定ファイルに出す)

## 5. ドメインルール

### 5.1 キッティングNo.

形式: `ファイルNo.-回-生産ライン-発行年月日-その日の発行順`

例: `0722-2-S-251014-01`

| 部分 | 例 | 意味 |
| --- | --- | --- |
| ファイルNo. | 0722 | 生産機種 |
| 回 | 2 | 1=1回目、2=2回目 |
| 生産ライン | S | ラインのコード |
| 発行年月日 | 251014 | 2025-10-14(**生産日ではない**) |
| 発行順 | 01 | その日の発行順 |

- 取込時に5つに分解して保存する。計画の識別キーは、既存アプリと同じ **「キッティングNo.+ロットNo.」**
- 回は既存DBの面(production_side)を正とし、キッティングNo.の回と食い違ったら警告する。ラインも同様に実装ライン(mounting_line)を正とする
- 正規表現は例から推定したもの(`^([^-]+)-([12])-([^-]+)-(\d{6})-(\d+)$`)。各部分の桁数は実データで確認する。形式に合わない番号は取り込まずに警告を出す
- **日程だけの変更では番号は変わらない。数量などの内容の変更では番号が振り直される**

### 5.2 計画データの項目

既存アプリの月次DBの `kitting_plan_items`(1行=1計画=1面)から読む。

| 本アプリの項目 | 既存DBの列 | 備考 |
| --- | --- | --- |
| キッティングNo. | kitting_list_no | |
| ロットNo. | lot_no | |
| 品名 | board_name | |
| ファイルNo. | setup_file_no | |
| ライン | mounting_line | |
| 回 | production_side | "1"=1回目、"2"=2回目 |
| 数量 | planned_qty(REAL) | その面の予定生産数。整数でなければ警告 |
| 累計 | cumulative_qty_external | |
| 発注数 | order_qty | |
| 計画開始・終了 | plan_start_datetime / plan_end_datetime | 書式 `2026/07/01 00:00:00`(日本時間として扱う) |
| 納期 | deadline | |
| 削除 | delete_flag | 立っていれば取消として扱う(意味は要確認) |
| 状態 | status | 値の意味は要確認 |
| 想定タクト | master.db `production_side_master.takt_time`(TEXT) | ファイルNo.・実装ライン・面ごと。書式は要確認 |

既存DBには actual_start_datetime / actual_end_datetime(実際の開始・終了)の列もある。実績の反映で埋めるかどうかは、実績の取込口の仕様と一緒に決める。

- 数量: この計画で生産する数(既存アプリは実績登録時の数の確認にこの列を使う)
- 累計: これまでに生産した累計(既存アプリの値を正とし、本アプリで足し込まない)
- 発注数: ロット全体の数
- 想定タクトは回ごとに異なる(表と裏で違う)

### 5.3 組(1回目と2回目)

- 組のキー: **ロットNo. + ファイルNo. + 数量**。品名は確認用(食い違ったら警告)
- 1回目か2回目かは、キッティングNo.の回の部分で判断する
- 同じロットを別の日に分けて作ることは多いが、同じ日に同じロット・同じファイルNo.・同じ数量の計画が重なったことはない。万一重なった場合は、発行日と発行順が早いものどうしを組にし、管理画面に警告を出す

### 5.4 回の工程

各回で、次の工程の開始・終了を記録する。段取りと片付けは回ごと(表と裏で別々)に行う。

| 工程 | 入力 | 必須 |
| --- | --- | --- |
| 段取り | 開始・終了 | ○ |
| N1チェック | 開始・終了 | ○ |
| 生産 | 開始・終了・生産数(区切りごと) | ○ |
| 初品チェック | 開始・終了 | ○ |
| X線検査 | 開始・終了 | 省略あり |
| 片付け | 開始・終了 | ○ |
| NG数 | 数値(回ごと) | |
| 備考 | 自由記入 | |

ルール:

- **生産の区切り**: 画面は「生産開始」「生産終了(生産数)」を繰り返し押す形にし、区切り番号は自動で振る。2回目以降の区切りを開始するときは、再開理由(人員交代、トラブル停止、計画切替など。停止理由マスタから選ぶ)を記録する
- 区切りは記録用紙の欄が3つなので、画面上の目安は3回。**データ上は上限を設けない**
- **工程は繰り返し記録できる**(例: トラブルで別の計画に切り替え、戻ってから段取りをやり直す)
- 異なる工程どうしは時間が重なってよい(例: 生産中に初品チェック)
- 同じ回の生産の区切りどうしは重ならない。同じ工程の二重開始と、開始していない工程の終了はサーバーで拒否する
- 計画をまたぐ重なりは基本的にないが、トラブルで今の計画を止めて別の計画を生産することはある。計画の順番の入れ替えもある(最終的に生産がそろえばよい)

### 5.5 付帯作業(ライン単位)

計画の合間に起きる、ラインを止める出来事。**計画には結びつけず、ラインに記録する。**

| 種類 | 追加の入力 |
| --- | --- |
| 部品探し | |
| 欠品 | |
| マシントラブル | 設備を選ぶ(設備マスタ) |
| 立上立会 | |
| 応援・その他 | |
| その他トラブル | 理由の記入(必須) |

- 開始・終了と、開始した人・終了した人を記録する
- **稼働率の計算からは外すのが既定**。ただし種類ごとに「稼働率に含めるか」の設定を持ち、定義が決まったら切り替えられるようにする
- 種類はマスタで追加・変更できるようにする
- 生産の区切りの再開理由と、付帯作業の種類は、共通の理由マスタで持つ(マシントラブルの合計時間を、計画の中か合間かに関係なく集計できるように)

### 5.6 誰がやったか

- すべての記録に、開始した人と終了した人を別々に持つ(人員交代で変わるため)
- ラインごとに「今の担当者」を設定し、ボタン操作の記録に自動で付ける。担当者は始業時と人員交代時に切り替える。1回の操作だけ別の人にすることもできる

### 5.7 完了と実績の反映

- **片付け終了 = その回の完了。** このとき次を行う
  - その回の稼働率を計算して保存する
  - その時点の計画数と想定タクトを、実績と一緒に保存する(後で計画が変わっても、過去の稼働率や日報が変わらないように)
- **製品の最終の回が完了したら、既存アプリへ実績を反映する**
  - 製品の完成数 = 最終の回の生産数(区切りの合計)。1回目と2回目を足さない
  - NG数は回ごとに分けて返す(既存アプリが回ごとに持っている)
- 完了後の誤りは、管理者が訂正し(訂正履歴を残す)、区分「訂正」で再出力する

### 5.8 進捗率と稼働率

- **進捗率**: 各ボタン操作で更新する。計画の進捗率 = 生産数の累計 ÷ その計画の数量。ラインの進捗率の定義は未確定
- **稼働率**: 片付け終了で更新する。定義は未確定(時間稼働率、生産数、想定タクトに対する実績のいずれか)。**定義に関わらず計算できるよう、工程・区切り・付帯作業の開始と終了、生産数、想定タクトを漏れなく記録しておく**
- ロット全体の進み具合は、既存アプリの累計と発注数を参照して表示する

## 6. 既存アプリとの連携

### 6.1 計画の取得(既存 → 本アプリ)

- 既存アプリのSQLiteを**読み取り専用**で開き(SQLiteのURIで `mode=ro`)、一定間隔(既定1分、設定で変更可)で計画を読む。読み取りは短く終える
- 既存DBの構造に依存する処理は `integration/legacy_plans.py` に閉じ込める
- 差分は**自動で反映**する(計画は頻繁に変わるため、人の確認は挟まない)

既存アプリの計画の持ち方(「版」方式):

- 計画を変えると、前の行を `is_active = 0` にして、`version` を1つ上げた新しい行を足す。行は削除しない
- 「キッティングNo.+ロットNo.」で有効な行は1件まで(部分ユニークインデックス)
- **内容が同じでも、取り込み直すと版が上がる。** したがって本アプリは `version` では変化を判定せず、**内容を比べて**判定する(`services/plan_diff.py`)
- 本アプリが読むのは `is_active = 1` の行だけ。キッティングNo.が空の保留行(pending_kitting_plan_items)は読まない

| 状況 | 扱い |
| --- | --- |
| 実績がない計画の変更・削除 | そのまま反映する |
| 実績がある計画の日程・数量の変更 | 計画の値を更新し、実績はそのまま |
| 実績がある計画が既存側で消えた | 実績は消さず、状態を「取消(実績あり)」にして警告する |
| 番号の振り直し(内容変更) | 下の「引き継ぎ」を行う |

**引き継ぎ**: 実績のある計画が消え、同じ同期でロットNo.、ファイルNo.、回が同じ新しい計画が現れたら、引き継ぎの候補とする。候補が1つなら実績を自動で新しい番号へ移し、複数なら管理画面で選んでもらう。元の番号と引き継ぎの記録は履歴に残す。

### 6.2 実績の反映(本アプリ → 既存)

- 連携フォルダにCSVを書き出し、既存アプリに新設する取込口で取り込む
- 書き手は一時ファイル名(`.tmp`)で書き終えてから `.csv` に改名する。読み手は `.csv` だけを読む
- ファイル名: `result_YYYYMMDD_HHMMSS_<出力ID>.csv`
- 出力IDで二重取込を防ぐ。出力の明細(どの実績をどの出力で渡したか)を記録する
- 文字コード、列、実績日の定義は未確定(「11. 未確定事項」)

## 7. 画面

### 7.1 現場画面(タブレット)

1. **ダッシュボード**: 生産ラインを選ぶ
2. **ライン画面**: 3カラム構成

```
┌──────────────────────────────────────────────┐
│ 上部: ラインの稼働率 / 進捗率 / 今の担当者        │
├────────┬──────────────────────┬───────────────┤
│ 左     │ 中央                 │ 右             │
│ メニュー │ タイムテーブル(縦軸が時刻) │ 選んだ計画の     │
│        │ ・計画の枠(最新の順番)    │ 工程ボタンと入力欄 │
│        │ ・実績(押された時刻)      │ ・付帯作業のボタン │
│        │ ・付帯作業のブロック      │               │
└────────┴──────────────────────┴───────────────┘
```

- タイムテーブルで計画をクリックすると、右カラムにその回の工程ボタンが表示される
- 計画の枠は最新の計画の順番で、実績は実際にボタンが押された時刻で描く(順番が入れ替わっても実績は動かない)
- 付帯作業のボタンは、計画を選んでいなくても押せる

### 7.2 管理画面(PC)

- 日報: ラインの実績を24時間のガントチャートで表示する
- 計画の同期状況と警告(取消(実績あり)、引き継ぎの候補、組の食い違い、再印刷が必要)
- 実績の訂正(訂正履歴を残す)と再出力
- マスタ: ライン、設備、理由(停止理由・付帯作業の種類)、作業者、管理者
- 記録用紙の印刷

### 7.3 記録用紙

- A4縦1枚に、上半分が1回目、下半分が2回目
- **作業前に印刷して準備する。** 計画の情報を印字し、作業の記入欄を設ける
- 印刷はブラウザの印刷プレビューから行う(ワンクリック印刷は不要)。印刷用ページをReactで作り、CSSで `@page { size: A4; margin: 0 }` を指定する。日本語Webフォントを配信して見た目をそろえる
- 複数の製品を選び、1製品1ページで一度に印刷できるようにする
- 印刷後に計画が変わったものは、管理画面に「再印刷が必要」と表示する(印刷時の計画の値を記録して比較する)
- 試行中は一部の手書きを残す。**Webで入力する項目はWebの値を正とする**

### 7.4 QR読取

フェーズ1では作らない(タイムテーブルから選べるため)。選び間違いが目立った場合に、ハンディのバーコードリーダーでの読取を検討する。

## 8. データモデル(案)

| テーブル | 主な項目 | 役割 |
| --- | --- | --- |
| plans | kitting_no + lot_no(複合キー)、legacy_plan_item_id、legacy_version、file_no、run_no、line_code、issue_date、issue_seq、lot_no、product_name、qty、cumulative_qty、order_qty、planned_start、planned_end、takt_sec、status、synced_at | 既存から取得した計画(1行=1回) |

- 削除はしない。取り消しは状態で表す

## 9. 非機能要件

| 項目 | 方針 |
| --- | --- |
| 同時アクセス | uvicornは1プロセス。SQLiteはWAL。端末数台を想定 |
| 認証(現場) | 現場端末はライン単位で使い、記録者は「今の担当者」で特定する(PINの要否は未確定) |
| 認証(管理) | 個人アカウントとパスワード(ハッシュで保存) |
| HTTPS | フェーズ1は不要(カメラもPWAも使わないため)。必要になったら社内用の証明書を導入する |
| 時刻 | サーバーの時刻で記録する。担当者PCのWindows時刻同期を有効にする |
| バックアップ | SQLiteのバックアップ機能(`backup()` または `VACUUM INTO`)で、毎日定時と更新前に共有フォルダへ保存する。起動中のファイルコピーはしない |
| ログ | アプリのログはファイルに日ごとに分けて保存する |
| 障害時 | 担当者PCが止まっている間、現場は紙に記録し、復旧後に管理者が代理入力する(入力者と入力日時を残す) |
| 常時稼働 | タスクスケジューラ(またはWindowsサービス)で自動起動。稼働時間中はスリープ無効。IPアドレス固定。ファイアウォールはアプリのポートだけ許可 |

## 10. 開発・配布・運用

担当者PCのフォルダ構成:

```
C:\GenbaApp\
  app\v1.0.0\        実行ファイル(版ごとにフォルダを分ける)
  data\genba.db      本番DB
  data\config.toml   ポート、既存DBのパス、連携フォルダ、バックアップ先、同期間隔
  exchange\          連携フォルダ
  logs\
```

ビルド(開発者PC): フロントエンドをビルド → テスト → PyInstallerでまとめる → 版番号付きのzip

更新(担当者PC): 停止 → 新しい版のフォルダを置く(旧版は残す)→ 起動(起動時にバックアップとAlembicを自動実行)→ 稼働確認の画面で確認。問題があれば旧版と更新前のバックアップに戻す。
