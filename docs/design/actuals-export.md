# 実績の書き出し(既存アプリに戻すための CSV)の設計メモ

開発指針(docs/spec.md)の 5.9(実績の書き出し)と 6.2(実績の反映)の、実装の判断の理由と細かい内容。
対象は `backend/app/domain/allocation.py`、`backend/app/domain/kitting_no.py`(`without_run`)、`backend/app/services/actuals_rows.py`、
`backend/app/services/side_links.py`、`backend/app/services/actuals_export.py`、`backend/app/api/admin_actuals.py`、`frontend/src/admin/actuals/`。

- 既存アプリのDBには書かない。本アプリは CSV を連携フォルダに置くだけで、取り込むのは既存アプリの取込口(これから作る)
- 想定タクトは既存アプリの production_side_master.takt_time(1枚あたりの秒)

## 行の単位(1行 = キッティングNo.+ロットNo.)

対象は、片付けが終わった計画(有効な完了がある計画のまとまり)。完了日(最新の有効な完了の、片付けの終了の稼働日)で期間を絞る。

| ロット | 出す行 |
| --- | --- |
| 面1と面2がキー H でつながる、または人が確定した | 面2の (キッティングNo., ロットNo.) の行。NG面1 と NG面2 を両方持つ。面1の行は出さない |
| 同じ (ロットNo., ファイルNo.) に面2の計画が無い | 面1の行(NG面2 は 0) |
| 面2の計画があるのにつながらない面1(未確定) | 書き出さない(警告)。「ひも付けの確認」に出す |
| 「つながない」と確定した面1 | 書き出さない(警告) |
| つながる面1が無い面2 | 面2の行を単独で出す。NG面1 は 0 で、注意書きを出す |

- 理由: 既存アプリは「製品の完成数 = 最終の回の生産数」で持つ(5.7)。面2がある製品は面2が最終の回なので、面2の行にまとめる。面1の計画が先に完了しても、面2が完了するまでは一覧に出ない
- ひも付けたが完了していない面1の計画があれば、面2の行に注意書きを出す(書き出しは止めない)
- 未確定・つながないの面1の行も一覧には出す(書き出さない行として)。キッティングNo.ごとのロットの合計の確かめを、今までどおり行えるように

### ひも付けのキー H(2026-10-25 に変更)

- **キー H = ロットNo. + キッティングNo.から「回」を除いた部分(ファイルNo.-ライン-発行年月日-発行順)**(`domain/kitting_no.py` の `without_run`)
- 変えた理由: 前のキー A(ロットNo.+ファイルNo.)では、同じロットを日を分けて作ると面1と面2が2件ずつ以上になり、どれを組にするか決まらない行が約2割あった(下の試算)。発行年月日などを足した案(E〜G)は外れる行が減るが、まだ取り違えの余地が残る。H は面ごとに一意なので、決まらない・取り違えが起きない
- そのかわり、面1と面2の発行のしかたが違う(発行日や発行順が違う)組は H でつながらない。これは推測で組にせず、管理者が「ひも付けの確認」で確定する(下)
- 面1を単独で出すのは、同じ (ロットNo., ファイルNo.) に面2の計画が1件も無いときだけ。面2があるのにつながらない面1を単独で出すと、既存アプリには面1の数が完成数として入ってしまうため

### ひも付けの確認(人が確定する方式。`services/side_links.py`)

- 対象: 一覧に出るキッティングNo.のロットについて、同じ (ロットNo., ファイルNo.) に面2の計画があるのに H でつながらない面1の計画(有効な計画だけ)。面1が完了していなくても出す(面2の行の NG面1 を決めるため)
- 候補: 同じ (ロットNo., ファイルNo.) の有効な面2の計画。発行日が最も近いもの(同じ近さならキッティングNo.の順で先のもの)を初期の選択にする。すでにほかの面1とつながっている面2(H でも、確定でも)は選べない(1つの面2の計画につながる面1は1つ。NG面1 をどの面1から取るか決められるように)
- 確定: 管理者が面2の計画か「つながない(面1は書き出さない)」を選ぶ。表 side_links(マイグレーション 0013)に、ロットNo.・面1のキッティングNo.・面2のキッティングNo.(つながないは空)・確定した人・日時を残す。やり直しは新しい行を足して上書きする(同じ面1の最新の行を使う。履歴は消さない)
- 確定した組は、H でつながった組と同じに扱う(面1のロットは面2の行にまとめ、NG面1 もそこへ)。AD-19 から、現場の作業者の紐づけも同じ表に入り、管理画面には誰がいつ紐づけたか(現場 / 管理者)を出す。作業者の紐づけ済みのものも、管理者が直せる(「外す」もできる)
- 確定した面2の計画が取り消されたら、その面1は未確定に戻る
- 確定したもの・つながないとしたものも一覧に出し、やり直せるようにする。未確定の件数は、書き出しの画面の上に出す(書き出し自体は止めない。つながっている行は書き出せるので)
- API: `GET /api/admin/actuals` の応答に `link_checks`(確認の一覧)と `pending_links`(未確定の数)を入れる。`POST /api/admin/actuals/links`(本文: lot_no、side1_kitting_no、side2_kitting_no。null は「つながない」)。H でつながっている・面2が無い・選べない面2なら 409、面1の計画が無ければ 404。ログインが要り(401)、`X-Genba-Admin` ヘッダーが要る(403)

## 現場の画面での紐づけと、優先順位(AD-19、2026-11-03)

24時間稼働で管理者がすぐに対応できないため、2回目(面2)の作業者が、現場の画面で1回目(面1)のキッティングNo.を入れて紐づける。**この紐づけを、そのまま書き出し(13列の CSV)に使う。管理者の確定は待たない。**

**保存先の判断(まず調べたこと)**: 管理者が確定した紐づけは表 `side_links`(0013。面1のキッティングNo.・ロットNo.・面2のキッティングNo.(つながないは空)・確定した人・日時)にあり、書き出しは `services/side_links.py` の `link_for_side1`(面1の側)と `side1_for_side2`(面2の側)で、「キー H でつながるか、`side_links` の最新の行(確定)か」を見ていた。新しい表は作らず、**`side_links` を広げた**(マイグレーション 0018): 操作 `action`(link / unlink=外す / skip=管理者の「つながない」)、した人の種類 `source`(field / admin)、前の相手 `previous_partner`、変えたとき書き出し済みだった日時 `exported_at`、管理者の確認済み。管理者と作業者の紐づけを1か所にまとめ、`services/side_link_store.py` の `current_links` が履歴を作った順に読んで「今有効な紐づけ」にする(読み方は1つ)。現場の画面からの行は `lot_no` が空(キッティングNo.の組)。古い管理者の行は lot_no を持つが、組として同じに読む(ロットの対応はロットNo.で決めるので、lot_no は使わない)。

**規則**:

- 紐づけは面2のキッティングNo.と面1のキッティングNo.の組。ロットは、ロットNo.が同じもの同士を対応させる(plan_item_id は使わない)。面2にあって面1に無いロット、面1にあって面2に無いロットは、対応が無いものとして、今までどおり(つながる面1が無い面2の行 / 面1の行を単独で)出す
- **優先順位: 明示の紐づけ(作業者または管理者)がある組はそれを使い、無い組は今までどおりキー H で自動につなぐ。** 明示の紐づけはキー H より優先する。明示で別の面1と紐づいた面2は、キー H の相手を失う(その面1は未確定に戻り、「ひも付けの確認」に出る)
- 1つの面1は1つの面2とだけ、1つの面2は1つの面1とだけ紐づく(キー H のつなぎも含めて数える)
- 作業者も管理者も、いつでも紐づけを直したり外したりできる。**最後に保存したものが有効**。管理者の確定のあとでも、作業者は直せる。外すと、キー H の自動のつなぎに戻る(キー H のつなぎそのものは外せない)。取り消しの印がある計画は紐づけられない(紐づけた計画が取り消されると、その紐づけは使わない)
- 引き継ぎ(AD-16)で管理者が実績を新しいキッティングNo.へ移したときは、紐づけも新しいキッティングNo.へ移す(新しい行を足す。移す先にすでに紐づけがあれば移さず、警告)
- 1回目と2回目でラインが違う組(例 1回目 Aライン、2回目 Cライン)も紐づけられる。キー H はラインを含むのでつながらないが、明示の紐づけならつながる

**現場の画面(`SideLinkPanel`)**: 面2の計画に「1回目のキッティングNo.」の欄と「紐づける」を出す(作業中でも、片付けの終了後でも。現場画面の表示範囲の計画が対象)。作業者ID(今の担当者)が必須。入力は前後の空白を除き、全角の数字・英字・ハイフンを半角にして探す(英字の大文字・小文字の違いは、1つに決まれば当てる)。欄の初期値は、明示の紐づけが無いとき、1. キー H でつながる面1、2. 同じロットNo.・ファイルNo.の面1の有効な計画がちょうど1つ(ライン・発行日・発行順は問わない)。無いか複数なら空欄にし、複数なら一覧から選べる。確かめること(`POST /api/runs/{kitting_no}/side-link/check`): 面1(回=1)の有効な計画がある、ファイルNo.が同じ、その面1がほかの面2と紐づいていない(相手を出して断る。先に相手を外す)は**断る**。ロットNo.の組が違えば合わないロットを出して**警告**し、確認すれば紐づけられる。紐づけ済みなら相手と「直す」「外す」。面1の画面は、紐づいた面2を表示するだけ(逆向きの入力は無い)。

**書き出し済みの計画の紐づけが変わったとき**: 現場の画面は、保存の前に「書き出し済みです。既存アプリの値は管理者が直す必要があります」の確認を出す(断りはしない)。書き出したかどうかは、書き出した行を表 `exported_rows` に記録して判る(0018。古い書き出しは保存した CSV から作った)。変えた行に、そのときの最後の書き出し日時を持たせ、管理画面の実績の書き出しに「書き出し後に紐づけが変わった計画」(計画、前と後の相手、変えた人と日時、最後の書き出し日時)を出す。管理者が既存アプリの値を直したら「確認済み」にすると消える。

**記録**: 紐づけ・直し・外しは `side_links` に行を足す(した人 = 作業者または管理者、日時、前の相手)。物理削除しない。`audit_log` にも残す。

## 「面1のキッティングNo.」の列を足した理由(書式版 2、2026-10-25)

- 既存アプリは、NG を「面1 = 面1の欄 + 面2の欄」の形で、面1と面2の計画ごとに持つ。面2の行の NG面1 は、**どの面1の計画のロットのNGか**が分からないと、既存アプリは入れ先を決められない
- 既存アプリが、ロットNo.とファイルNo.などから面1の計画を**推測しなくてよい**ように、本アプリが決めた面1のキッティングNo.を行に添える。ひも付けの決め方(キー H と、管理者が確定した組)は本アプリが持つので、そこで決めたものをそのまま渡す
- 値は面2の行だけ。NG面1 が 0 でも、つながる面1があれば入れる(NG が無かったことも、その面1の計画に対するもの)。つながる面1が無い面2の行と、面1の行は空にする(空なら、既存アプリは面1の計画を探さず、NG面1 の 0 を使わない)
- 列は最後に足し、前の12列の並びは変えない。それでも列の数が変わるので、書式版を 2 に上げた(取込口が、12列の版 1 と13列の版 2 を区別できるように)
- 書き出し日時の形も、この版で YYYY-MM-DD HH:MM:SS(日本時間、タイムゾーンなし)に固定した(取込口が読み方を決められるように)

## 生産数のロットへの割り振り(`domain/allocation.py`)

- ロットの並び順(ロットNo.の順。画面のロットの一覧と同じ)に、各ロットの計画数まで入れ、余りは最後のロットに入れる。ロットが1つなら全部をそのロットに入れる
- 合計が計画数の合計に届かなければ、後ろのロットほど少ない(0 もある)
- 実際にどのロットをいくつ作ったかは記録していない(工程の記録はキッティングNo.の単位。5.4)ので、画面で行ごとに直せるようにした
- 書き出すときに、キッティングNo.ごとに「直した数(直していない行は割り振り)+ 一覧に出さないロットの割り振り」の合計が累計と一致するか確かめる。一致しなければ 409 と日本語の理由。画面も同じ計算で、書き出しのボタンを押せなくし、理由を出す

### 割り振りの保存と優先順位(AD-18d、2026-11-03)

割り振り(キッティングNo.ごとの生産数の合計を、ロットに分けた値)を保存できる。**実績の記録(`run_events` など)は変えない**。別のテーブルに履歴として残す。

- 保存先: `lot_allocation_changes`(0019)。キッティングNo.ごとの履歴で、**行は消さず追加するだけ**。1行 = 保存 / 元に戻す / 引き継ぎで移ってきた / 引き継ぎで移っていった。前と後の {ロットNo.: 数}、した人(作業者ID)、日時、現場か管理者か(source)、書き出し済みだった日時を持つ。キッティングNo.ごとに**最後の行が有効**で、有効なのは最後の行が「保存」か「引き継ぎで移ってきた」のときだけ(元に戻すと今の規則に戻る)。audit_log にも同じ内容を残す
- 優先順位(`services/lot_allocation.effective`): **保存した割り振り > 今の規則**。保存したものが使えるのは、ロットの組が今の計画と同じで、合計が今の生産数の合計と一致するときだけ。合わないとき(保存のあとに生産数を訂正したなど)は、**保存したものを使わず今の規則で計算し**、「割り振りを直す必要があります」を出す(生産記録票のページ、書き出しの画面の行の確認事項)
- 両面の組は、書き出しに使う面(面2、面2が無ければ面1)のキッティングNo.の割り振りを使う。生産記録票の数量 A の実績と、実績の書き出しは、同じ処理(`actuals_rows`)を通るので、必ず同じ値になる
- 現場(生産記録票のページの「割り振り」。ロットが2つ以上、完了していて、生産数の合計が計画数の合計と違うとき): 「差を引くロット」を1つ選ぶと、ほかのロットを計画数どおりにし、選んだロットを「生産数の合計 - ほかの合計」にする(`domain/allocation.balance`)。0 未満になるときは、その選択はできないと出す(数を直接直してもらう)。数を直接直してもよいが、合計が生産数の合計と合わないと保存できない。「元に戻す」で今の規則に戻る。保存・元に戻すは作業者ID必須
- 書き出し済みの計画の割り振りを変えるときは、AD-19 の紐づけと同じく、保存の前に「書き出し済みです。既存アプリの値は管理者が直す必要があります」を確認し、管理画面の「書き出し後に紐づけ・割り振りが変わった計画」(`/api/admin/actuals/link-changes`。種類 `kind` = link / allocation)に出す。管理者が「確認済み」にすると消える
- 管理者が書き出しの画面で直した数は、**書き出すときに同じ場所へ保存する**(source = admin)。これは今書き出す値なので、「書き出し後の変更」には出さない。書き出しの画面の初期値は、保存した割り振り(無ければ今の規則)
- 引き継ぎ(AD-16)で実績を新しいキッティングNo.へ移したときは、保存した割り振りも移す(新しい側に「引き継ぎで移ってきた」、古い側に「移っていった」を追加)

| メソッド | パス(現場。IP 制限だけ) | 説明 |
| --- | --- | --- |
| GET | `/api/runs/{kitting_no}/allocation?balance_lot_no=` | 今の割り振り。`balance_lot_no` を付けると、そのロットで差を調整した提案(保存しない。0 未満なら `proposal_error`) |

## CSV と保存

- BOM 付きの UTF-8、改行は CRLF。見出しの列(13列。最後に足した): 書式版、書き出し日時、元のDB(フォルダ名)、キッティングNo.、ロットNo.、ファイルNo.、面、日付、生産数(累計)、NG面1、NG面2、担当者ID、面1のキッティングNo.
- 保存先: `<exchange_dir>\actuals\actuals_<年月日>_<時分秒>_<書き出しの番号4桁>.csv`。一時ファイル(`.tmp`)に書き終えてから改名する(読み手は `.csv` だけを読む)
- 書き出しの履歴(表 actuals_exports): いつ・誰が・何行・ファイル名・絞り込みの条件と、CSV の中身。画面からのダウンロードは履歴の中身を返す(取込口が連携フォルダのファイルを動かしても、ダウンロードできるように)
- 保存できなければ 409 で、履歴も残さない
- **Excel で開いて保存した CSV は、ロットNo.などが壊れるので、保存せずに取り込む。** Excel は、先頭が0の番号(ファイルNo. `0722` など)の0を消し、数字だけの長い番号を指数の形にし、日付に見える値を日付に変える。保存すると、その形で書き換わる。画面の書き出しのボタンの下にも同じ注意を出す
- 書き出しても実績の記録は変えない(書き出し済みの印も付けない)。同じ内容を何回書き出しても、こちらの記録は変わらず、履歴とファイルが増えるだけ。値は累計なので、取込口が同じ行を何回取り込んでも、上書きすれば同じ結果になる
- 訂正のあとの出し直し(5.7 の区分「訂正」)は、今は同じ書き出しをもう一度行う形。区分の列は持たない
