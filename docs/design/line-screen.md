# ライン画面(現場画面)の設計メモ

開発指針(docs/spec.md)の 7.1 の実装の判断の理由。対象のコードは `frontend/src/field/line/` と `frontend/src/shared/`。

## 部品の分け方

| ファイル | 役割 |
| --- | --- |
| `LineScreen.tsx` | 全体の組み立て(選んでいる計画、出すダイアログ) |
| `TopBar.tsx` / `SideMenu.tsx` | 上部(ライン名・稼働率・ラインの進捗率・今の担当者)と左のメニュー |
| `Timetable.tsx` | 中央のタイムテーブル(計画の枠・実績・付帯作業の3列) |
| `StepPanel.tsx` / `LineEventPanel.tsx` | 右のパネル(工程のボタン・NG数・備考)と付帯作業 |
| `LineDialogs.tsx`、`dialogs/`、`OperatorPicker.tsx` | ダイアログ(テンキー、再開理由、確認、文字入力、付帯作業の設備・理由、担当者の交代) |
| `useBoard.ts` / `useLineActions.ts` / `useNow.ts` | board の読み直し、APIの呼び出し、今の時刻 |
| `timeScale.ts` / `steps.ts` | 表示から分けた計算(時刻と位置の変換、重なりの列、工程の状態)。vitest でテストする |

## APIクライアント

- 型は FastAPI の OpenAPI から `npm run gen:api` で生成する(`src/api/schema.ts`。手で編集しない)。バックエンドの venv の Python で `python -m app.openapi_export` を動かして OpenAPI を書き出し、openapi-typescript で型にする
- `scripts/gen-api.test.ts`(vitest)が生成し直して比べ、`schema.ts` がバックエンドと食い違っていれば失敗する(APIを変えたのに生成し忘れたことに気づける)
- 呼び出しは openapi-fetch(`src/shared/api.ts`)。手書きの fetch は使わない。APIの型が変わったら生成し直し、型エラーで気づけるようにする

## ボタン操作の送り方(src/shared/send.ts、useOperation.ts)

- request_id は操作ごとに1つ作り、成功するまで、同じ操作・同じ内容なら同じ値で送る(内容が変われば作り直す。同じ request_id で内容の違う操作を送ると 409 になるため)
- UUID v4 は `crypto.getRandomValues` から作る。`crypto.randomUUID` は安全な接続(HTTPS)でしか使えず、HTTP の社内LANでは使えないため
- 送信中は、そのボタンを押せない状態にする
- 担当者が未設定のまま記録のボタン(工程・NG数・備考・付帯作業)を押したら、サーバーに送らず、先に担当者を選ぶ画面を出す(送っても 409 になるだけで、押し直しの手間が増えるため)
- テンキーの画面は、送信が成功するまで閉じない。失敗したら理由を画面の中に出し、入力した数は消さない(入れ直しの手間と、入れ間違いを防ぐため)
- 通信の失敗と 503 は、同じ request_id で自動で1回だけ送り直す。それでも失敗したら理由を画面に出す
- 409 と 404 は送り直さず、応答の detail をそのまま出す(サーバーの文は画面にそのまま出せる日本語にしてある)
- 成功したら、すぐに board を読み直す。ダイアログは送る前に閉じ、結果はお知らせと board で分かるようにする

## 画面の更新

- board は5秒ごとに読み直す。画面が非表示のあいだ(visibilitychange)は止め、表示に戻ったらすぐ読み直す
- 古い応答があとから届いても、新しい応答を上書きしないようにする
- 今の時刻の線と経過時間は、端末の時計で10秒ごとに更新する(記録の時刻はサーバーが付ける)

## 稼働日と表示範囲(2026-10-21 に追加)

- **稼働日を 8:15 で区切る理由**: 現場の1日は朝の始業(8:15)から翌朝までで、夜勤の計画を暦の日付で切ると、1つの稼働日の計画が2日に分かれてしまうため。区切りの時刻は `schedule.day_start` で変えられる(`domain/workday.py`)
- **表示範囲を48時間にする理由**: 前の稼働日の終わりの作業(夜勤の続き)と、次の稼働日の始まりの計画(先行して始めることがある)を、同じ画面で見られるようにするため。稼働日の前後12時間ずつを足す
- **ライン画面に出す計画の条件**(`services/plan_query.py` の `board_plans`)
  - 表示範囲と重なる計画に加えて、表示範囲の中に実績がある計画(先行)と、始めたが片付けが終わっていない計画(遅れ。日付は問わない)も出す。遅れている計画を、計画の日付が過ぎたからといって画面から消すと、記録の続きができなくなるため
  - 計画終了が過ぎたのに未着手の計画は出さない。画面が過去の計画で埋まらないようにするため。必要なら検索で選ぶ
- **ラインの進捗率**は、稼働日(8:15〜翌8:15)と重なる計画で計算する。表示範囲(48時間)で計算すると、前後の稼働日の計画まで入ってしまうため。画面に出さない「未着手で過ぎた計画」も計画数に含める(出さないのは表示の都合で、遅れていることには変わりないため)
- **今の時刻の線**: board の `server_time` と、タブレットで送った時刻・受け取った時刻の真ん中を比べて、時計の差を補正する(`clockOffset`)。記録の時刻はサーバーが付けるので、線もサーバーの時刻に合わせる。5秒ごとに動かす
- **表示範囲の外の計画**を検索で選んだときは、`GET /api/runs/{kitting_no}/{lot_no}` で1件だけ読み、board を読み直すたびに読み直す(`useSelectedPlan.ts`)

## 計画の検索

- 英字の大文字・小文字と全角・半角の違いを無視するため、サーバーで NFKC と casefold をかけて比べる(SQLite の LIKE ではできない。有効な計画は数千件程度なので、全件を読んでも短く終わる)
- キッティングNo.が完全に一致する1件は Enter でそのまま選ぶ。将来、バーコードリーダー(キーボードとして文字と Enter を送る)で読み取れるようにするため。一致が2件(ロット違い)のときは、結果から選んでもらう

## タイムテーブル

- 縦軸は表示範囲の48時間。1時間 = 90px。稼働日の境目(8:15)に線と日付を出す
- 時刻と位置の変換は、表示範囲の始まりを基準に、端末の時間帯によらず日本時間で計算する(`timeScale.ts`)
- 終了していない記録は、今まで伸ばす。表示範囲からはみ出す計画の枠は端で切り、「表示範囲の前から続く/後へ続く」の印と破線を付ける
- 重なる計画・記録は横に並べる(空いた列は使い回す)。短い記録も工程名が読めるよう、最低の高さを付ける
- 工程ごとの色に加えて、工程名と「作業中」の文字も出す(色だけで区別しない)

## タブレット向けの決まり

- 押す部分は高さ 56px 以上、本文 16px 以上、ボタン 18px 以上。ホバーに頼る表示はしない
- 画面の幅 1024〜1366px(横向き)で横にはみ出さない(Playwright で確かめる)
- 背景を押してもダイアログは閉じない(押し間違いを防ぐ)。閉じるのは「やめる」だけ
- 担当者が未設定なら、案内を出す(ボタンを押すとサーバーが 409 を返し、その理由を出す)

## 画面の確認(Playwright)

- `npm run e2e` で、確認用のデータ(`python -m app.cli demo-seed`)を入れたDBを毎回作り、ビルドした画面をバックエンドが配信する形で操作する(`e2e/serve.mjs`)
- 撮る時刻によって画面が変わらないよう(「過ぎて未着手」の計画は時刻で変わる)、e2e ではサーバーの時計を環境変数 `GENBA_CLOCK_START`(2026-10-21 10:00)から進める(`app/core/clock.py`)
  - 本番で誤って設定されると、すべての実績の時刻がずれて記録されるため、二重に歯止めをかける: `GENBA_TEST_MODE=1` も設定されているときだけ有効(片方だけなら無視して警告)。exe(PyInstaller、`sys.frozen`)では設定に関わらず常に無効
- 画面の大きさは 1280×800(タブレットの横向き)。スクリーンショットは `frontend/test-results/screens/`(Git の対象外)
- 画面の文言は辞書(`src/i18n/`)から出す。Playwright は既定の日本語の文言で要素を探す。⑭ はベトナム語に切り替えた画面(詳細: docs/design/i18n.md)
