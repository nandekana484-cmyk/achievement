## 既存アプリの調査結果(2026-10-20 / 2026-10-21、既存アプリ側AIの調査)

### 計画の持ち方(kitting_plan_items)

- 計画は月次DBの `kitting_plan_items`(1行=1計画=1面)
- 計画を変えると、前の行を `is_active=0` にして、`version` を1つ上げた新しい行を INSERT する「版」方式。行は消さない
- 「キッティングNo.+ロットNo.」で有効な行は1件まで(部分ユニークインデックス)
- **内容が同じでも、取り込み直すと版が上がる。** そのため変化の判定に `version` は使えず、内容(`LegacyPlan.content()`)で比べる
- キッティングNo.が空の保留行(pending_kitting_plan_items)は読まない
- `created_at` / `updated_at` は `YYYY-MM-DD HH:MM:SS`(PCのローカル時刻=日本時間)
  - 新しい版を作ると、古い行は `is_active=0` と `updated_at` だけが更新され、新しい行は INSERT 時刻になる
  - 前月からの引き継ぎ(ロット単位)でコピーした行は、コピーした時刻になる(元の時刻は写さない)
  - 「削除(ソフト)」は、そのバッチの有効な行を `is_active=0` にして `updated_at` を更新する
  - 実績の登録などでは、計画の行は書き換えられない
  - バックアップから戻したDBは、元の時刻のまま
- `delete_flag`: 2026-10-31(AD-16)から、既存アプリの有効な計画の条件に合わせる(下の「有効な計画の条件」)。それまでは意味が分からず、実データでもすべて0だったので判定に使っていなかった
- `status` は値の意味が分からない → 保存するだけ

### フォルダの構成とDBの設定

- `<既存アプリのフォルダ>\db\<フォルダ名>\inventory.db` が月次DB(フォルダ名は自由)
- `<既存アプリのフォルダ>\db\inventory.db` は「未選択」を表す既定DB(読まない)
- `<既存アプリのフォルダ>\db\master.db` は共通マスタ
- どのDBも `journal_mode=delete`(WALではない)。既存アプリの接続の待ち時間は30秒
  - 読み取り中は既存アプリの書き込みを待たせるので、**DBごとに接続を開き、1つの読み取りトランザクションで必要なものを読んで、すぐ閉じる**
  - 書き込み中で一時的に開けないときは、少し待ってやり直す(`open_readonly`)

### 有効な計画の条件と古い計画の判定(AD-16。既存アプリ 5.0.0 以降、月次DBの版 16)

既存アプリの `docs/domain/plan_stale.md` に合わせる。**既存アプリの前提: 月次DBの版は 16、ビュー `v_plan_stale` は 5.0.0 以降の既存アプリでその月次DBを一度開くとできる**(開かれていない古い月の月次DBには無い)。

- **有効な計画の条件**: `COALESCE(is_active, 1) = 1 AND COALESCE(delete_flag, 0) = 0`(`integration/legacy/plans.py` の `_PLAN_SQL`)。`delete_flag=1` になった計画は「読めなくなった」扱いで、今までどおり取消の印(理由 `vanished`)を付ける(行は消さない)。ロットごとの最終書き込み時刻(正のDBの判定)は、今までどおり無効な行も含める
- **キー**: `(kitting_list_no, lot_no)` の前後の空白を除いた値。ロットNo.の NULL は `''`(既存アプリは `''` で入れる。ビューも NULL を `''` で返す)。2026-10-31 以前から、本アプリは `str(lot_no or "").strip()` でロットNo.を整えていた
- **同じキーの有効な行が2行以上**(一意の索引の無い古い月次DBだけ): 黙って捨てず、警告(plan_sync_warnings)を出し、**更新日時(updated_at、無ければ created_at)が新しい方**を採る(同じなら行番号 plan_item_id が大きい方)。同期は止めない
- **ビュー v_plan_stale**: 有効な計画1件につき1行(`kitting_list_no, lot_no, is_stale, judge_reason, has_legacy_actuals, replacement_kitting_list_no, replacement_count, latest_batch_id, judged_at`)。計画と同じ接続・同じトランザクションで、全件を1回で読む(1件ずつ引かない。2,500行で約0.05秒)。`is_stale=1` と `judge_reason='stale'` は対応する(食い違えば古くない扱い)

| judge_reason | 扱い |
| --- | --- |
| `stale` | 古い計画 |
| `in_latest_batch`、`outside_period` | 古くない |
| `date_unparsable`、`no_period`、`no_latest_batch` | 古くないとして扱い、DBごと・理由ごとの件数を同期の警告に出す |

- **古い計画で、現場アプリに実績が無い**: 取消の印(理由 `reissued` = 出し直し)を付ける。判定が古くないに戻れば、「再び現れた」と同じく元に戻す(理由も消す)。計画終了が今日の 0:00 より前でも取り消す(実績が無いので守る必要がない)。一度も有効にならなかった古い計画は取り込まない。**出し直しの取消も、取消の安全装置の件数に入れる**(分母にも同じ計画を入れる。分母は計画終了が今日以降の計画に限るが、出し直しは過去の計画も取り消すため)
- **古い計画で、現場アプリに実績がある**: 取り消さない。警告を出し、`plans.is_stale` と `replacement_kitting_no`・`replacement_count`(既存アプリの判定)を持って、「引き継ぎの確認」の対象にする。ライン画面にも「出し直しで古くなった計画」と出す
- **実績**: 取り消していない工程の記録、備考、NG数、完了のどれかがあるキッティングNo.(`plan_reconcile.kitting_nos_with_actuals`)。既存アプリ側の実績(`has_legacy_actuals`)は使わない(実績の扱いは現場アプリが自分の実績で決める)
- **ビューが無い・読めない月次DB**: 判定は「分からない」。新しく「出し直し」の取消はせず、前の同期で「出し直し」として取り消した計画は元に戻さない(前の状態を保つ)。警告を出す。同期全体は失敗にしない(計画そのものの取消・復活は今までどおり)。「読めないDBがあれば同期全体を error」の決まりは、計画の読み取りだけに残る
- **取消の理由**(`plans.cancel_reason`): `vanished`(読めなくなった。0016 より前に取り消したものも)、`reissued`(出し直し)、`carried_over`(引き継ぎ済み)。ライン画面・管理画面「引き継ぎの確認」・実績の書き出しの警告で区別して出す

### 実績の引き継ぎ(`services/handover.py`)

実績のある計画が取り消された・古くなったとき、管理画面の「引き継ぎの確認」に出す。**自動では移さない**。

- 対象: 実績があり、(古い計画(`is_stale`)、または取り消された計画(`vanished`・`reissued`))で、引き継ぎ済みでないキッティングNo.。取り消された計画は、移す先の候補があるものだけを出す
- 候補: 既存アプリの判定(`replacement_kitting_no`。`replacement_count` が2以上なら「候補が複数ある」と出す)と、同じロットNo.・ファイルNo.・回の有効な別のキッティングNo.
- 管理者が移す先を選んで確定すると、`run_events`・`run_inputs`・`run_ng_inputs`・`run_completions`・`run_corrections` の `kitting_no` を、**消さずに付け替える**(NG数の `side_kitting_no` も合わせる)。完了の写し(丁取り・目標タクトの写しを含む)は、写しのまま移る。移したあと、古い計画に取消の印(理由 `carried_over`)を付ける
- **移す先にすでに実績があるときは確定しない**(409。合わせ方は人が決める)。候補にない移す先、引き継ぎ済みの計画も断る
- **履歴は新しい表 `kitting_handovers`**(古い・新しいキッティングNo.、確定した管理者、日時、表ごとの移した行数、警告)と `audit_log` に残す。`run_corrections` は工程の記録1件ごとの訂正(対象の行・変更前後の項目)の履歴で、キッティングNo.の単位で複数の表をまとめて移す操作には合わないため、別の表にした。同じ古いキッティングNo.の行があれば引き継ぎ済み
- 警告(確定は止めない。結果と履歴に出す): 書き出し済みの CSV に古いキッティングNo.がある(既存アプリに二重に反映されるおそれ)、NG数のロットNo.が新しい計画に無い、「ひも付けの確認」の確定に古いキッティングNo.がある、ロットNo.の組が違う
- 移したあと、日報・区間 CSV・実績の書き出し・効率は、新しいキッティングNo.で出る(`tests/records/test_handover.py`)

### 想定タクト(master.db の production_side_master)

- 列は `setup_file_no`、`mounting_line`、`production_side`、`takt_time`(TEXT。中身は "30"、"55.72" などの小数)
- (ファイルNo.・実装ライン・面)ごと。キーは既存アプリと同じく正規化してから引く
- 正規化すると同じキーになり値が異なる行があったら、どちらとも決めず「読めない」扱いにして計画ごとに警告する
- `nan` / `inf` は受け付けない(`nan` は等しさの比較ができず、毎回「変更あり」になってしまうため)
- 単位は1枚あたりの秒(2026-10-23 に確定)

### 丁取り(master.db のビュー v_board_teitori)

- 既存アプリ 4.1.0 以降のビュー(`setup_file_no`、`mounting_line`、`part_no`、`teitori`、`status`、`fetched_at`)を、計画の同期のたびに全件読む。キーは正規化した (ファイルNo., 実装ライン) で、面は問わない
- 本アプリの表 `board_teitori`(0015)に上書きする。**計画と作業者と違い、読めなくても同期全体は失敗にしない**(ビューが無い・読めない → 前回の値を使い、`plan_sync_warnings` に警告、起動後の最初の1回だけログ)
- 丁取りの変化は計画の内容比較に入れない。詳細と確かめ方: [metrics.md](metrics.md)

### 正規化(domain/normalize.py)

既存アプリの `models/production_side_master.py` の `normalize_setup_file_no` / `normalize_mounting_line` を、結果が完全に同じになるよう移植した。数字だけのファイルNo.は文字列のまま `zfill(4)` する(int に変換しないので `"00004"` は `"00004"` のまま)。キッティングNo.のライン記号との比較も正規化した値どうしで行う。

## ロットごとに正とするDB(plan_source.py)

実績は計画(キッティングNo.+ロットNo.)に付けるものなので、計画がどの月次DBにあるかにはとらわれない。棚卸の期間が重なり、既存アプリでDBを行き来することがよくあるため、同じロットが複数のDBにあるときは **ロットごとに、最後に書き込まれたDB** を正とする。

- ロットの最終書き込み時刻 = そのDBのそのロットの全行(無効な行も含む)の `MAX(updated_at)`(空なら `created_at`)
  - 版の更新・削除(ソフト)・引き継ぎのコピーは `updated_at` を新しくするので、最後に触ったDBが正になる
  - バックアップから戻したDBは時刻が古いままなので、ファイルの更新日時が新しくても正にならない
- 同じ時刻のときは、DBファイルの更新日時が新しいほうを正とし、内容が違えば警告する。最後はフォルダ名で決め、結果を毎回同じにする
- 時刻が読めないロットは最も古い扱い
- 警告は、正とするDBの行のものだけを出す(古いDBに残った読めない行で警告を出し続けないため)。どのDBの行か分かるよう、警告の先頭にフォルダ名を付ける

## 取消にしない条件(plan_cancel.py)

| 状況 | 理由 |
| --- | --- |
| 月次DBが1つでも読めない | どのDBが正か決められない。何も反映せず error を記録する |
| 形式エラーで読めなかった行の計画 | 既存DBに行は残っている |
| 古い計画(出し直し)で実績がある | 取り消さず、警告と「引き継ぎの確認」(上の「古い計画の判定」) |
| 計画終了が今日の 0:00 より前 | 古い月次DBが読む対象(既定120日)から外れても、過去の計画を残す。警告も出さない(古いDBが外れるたびに過去の計画の警告が大量に出るのを防ぐ) |
| ロットがどの月次DBにも見当たらない | DBの置き場所の変更や読み込み対象の設定の間違いかもしれない。値も状態も変えず、警告を出す |

取消にするのは、ロットがどこかの月次DBにあり、かつ正とするDBにその計画が無いときだけ(理由 `vanished`)。このほかに、古い計画(実績なし)を `reissued` で取り消す。

### 一括取消の安全装置

1回の同期で取消が多すぎるとき(既定: 10件以上 かつ 分母の30%以上)は、設定の間違いなどを疑い、何も反映せずに `guarded` を記録する。

- 分子には出し直しの取消も入れ、分母にはその計画も入れる(AD-16)
- 分母は「有効な計画のうち、計画終了が今日の 0:00 以降(または空)のもの」。過去の計画は取消の対象にならないので、分母に入れると月日が経つほど安全装置が効きにくくなる(2026-10-21 の確認で直した)

## 同期の進め方(plan_sync.py / plan_sync_scheduler.py)

- 既存DBの読み取りと正とするDBの決定は、本アプリのDBの書き込みのロックの外で行う。本アプリのDBを読んで差分を反映する部分だけをロックする(詳細: docs/design/db-writes.md)
- 1回の同期は1トランザクション。失敗したら反映は取り消し、`result=error` を記録する。失敗の記録すら書き込みの混雑でできなかったときも、例外にせず次の回にやり直す
- 計画は物理削除しない。既存側で消えた計画は `status=cancelled`。戻ってきたら `active` に戻す(revived として数える)
- 内容が同じでも、既存側の行番号・版・正とするDBは変わることがあるので、追跡用の値だけは毎回合わせる(変更としては数えない)
- 新しいラインの記号を見つけたら lines に自動で登録する
- 定期実行は main.py の lifespan で始める asyncio のタスク。同期そのものは別スレッドで動かし、APIの応答を止めない。同期は同時に1つだけで、実行中に次が来たら `skipped` を記録する。1回の失敗で止めない
