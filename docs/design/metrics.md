# 効率と進捗率の設計メモ(AD-15)

開発指針(docs/spec.md)の 5.8「効率と進捗率」の、決めと実装の理由。画面のバー・日報・区間の CSV は、同じ計算(`services/metrics.py`)と同じ入力(`services/efficiency_inputs.py`)を使う。

## 変更前の計算の場所(置き換えたもの)

| もの | 場所 | 中身 | 今 |
| --- | --- | --- | --- |
| 稼働率 | `services/board.py`(`BoardOut.utilization`)、`RunCompletion.utilization` | 計算していなかった(常に null) | 効率に置き換え。`RunCompletion.utilization` の列は使わない(列は残す) |
| ラインの進捗率 | `services/board.py` の `_line_progress`、`BoardOut.line_progress` | 稼働日に重なる計画の生産数の合計 ÷ 計画数の合計 | 廃止。生産中の計画ごとの進捗率に置き換え |
| 計画の進捗率 | `services/board.py` の `board_plan_out`、`BoardPlanOut.progress` | 生産数の合計 ÷ 計画数 | 時間の進捗率に置き換え(下) |
| 表示 | `TopBar.tsx`、`Timetable.tsx`(枠の「%」)、`StepPanel.tsx`(計画の進捗率) | 上の値を出す | `BoardPlanOut.in_progress` / `progress` と `BoardOut.efficiency` を出す |
| 理由の「稼働率に含める」 | `reasons.counts_in_utilization`、管理画面「理由」 | 付帯作業を稼働率に含めるかの設定(未使用) | **そのまま残す**(効率は付帯作業の時間を分母に入れないので使わない。扱いは下の「未確定」) |

## 効率

```
効率 = Σ(目標タクト × 良品台数 ÷ 丁取り数) ÷ Σ(実所要時間)
```

- 目標タクト: `plans.takt_sec`(master.db の production_side_master.takt_time。1枚あたりの秒)。計画の取り込みが持つ値
- 良品台数: 生産の区切りごとに入れた数(NGを含まない)。÷ 丁取り数 で枚数にする。**切り上げない**(小数のまま)
- 実所要時間: 段取り・N1・生産・初品・X線・片付け、すべての工程の記録の時間。取り消した記録は入れない。作業中の記録は今の時刻まで数える
- **付帯作業の時間は分母に入れない**。工程と付帯作業が重なる分は、工程の時間から引く(付帯作業どうしが重なっても1回だけ引く)
- 対象: その稼働日に工程の記録がある計画(キッティングNo.)だけ。計画どうしの重なりは統合せず、計画ごとに足す
- 外す計画: 目標タクトか丁取り数が無い計画は、**分子と分母の両方から外す**。1 を仮定しない。外した件数と理由(丁取りの status、`no_row`、`no_takt`)を画面と日報に出す
- 例: 目標タクト60秒、4丁取り、良品480台 → 120枚 × 60秒 = 2時間。実所要2時間30分 → 80%(`tests/records/test_metrics.py`)

### 稼働日

稼働日(8:15 始まり、`schedule.day_start`)で集計する。境目をまたぐ記録は、時間を境目で分ける(`domain/intervals.split_by_workday`)。**良品数は区切りが終わった稼働日に数える**(区間 CSV の「生産数」と同じ規則。例: 8:00〜9:00 の生産は、10/20 には 15分、10/21 には 45分と良品数)。画面上部のバーは今日の稼働日(日付を指定した板ならその日)、日報はその日の稼働日。

### 計算の単位とロットの違い

計算の単位はキッティングNo.。同じキッティングNo.のロットで目標タクトか丁取りが違えば、警告(`EfficiencyOut.warnings`)を出し、**最初のロット(ロットNo.の順)の値を使う**(計画のまとまりの決まり。`KittingGroup` の ファイルNo.・ライン・面と同じ)。丁取りはロットのファイルNo.・ラインで引くので、ロットでファイルNo.かラインが違うときに起こる。実データ(2026-10-31、NANJYOU-H の `C:/work/inventory/dist` の 1771 キッティングNo.)では、ロットで目標タクトが違う例も、ファイルNo.・ラインが違う例も 0 件だった。

### 完了した計画

片付けの完了時に、丁取り数とその status を完了の写し(`run_completions.teitori_snapshot` / `teitori_status_snapshot`)に残す(目標タクトの写し `takt_sec_snapshot` と同じ所)。**完了した計画の効率は写しの値、作業中の計画は今の値**を使う。写しを残す前の完了(`teitori_status_snapshot` が空)は、今の値を使う。完了のあとにビューの丁取りが変わっても、完了した計画の効率は変わらない。

## 進捗率

```
進捗率 = その計画の工程の記録の時間の合計 ÷ 計画の時間
```

- 計画の時間 = 計画終了 − 計画開始(キッティングNo.のまとめ方は画面と同じ。最も早い開始〜最も遅い終了)。無い・0以下なら null(画面は「—」)
- 工程の時間の数え方は効率と同じ(取り消し除く、作業中は今まで、付帯作業と重なる分を引く)。稼働日では分けない(計画全体の進み具合)
- **生産中の計画だけ**出す: 最初の工程を始め(取り消していない記録がある)、片付けが終わっていない(有効な完了が無い)。片付けが終われば出さない
- 100% を超えてもそのまま出す(画面は色を変える)
- 例: 計画10時間、段取り30分、生産1時間30分 → 2時間 ÷ 10時間 = 20%
- 既存アプリの完成判定(良品 ÷ 計画数)は変えない。画面の「完了」は片付けの終了のまま

## 丁取りの取り込み

- 元: 既存アプリ(4.1.0 以降)の master.db のビュー `v_board_teitori`(列: setup_file_no, mounting_line, part_no, teitori, status, fetched_at)。表 `board_teitori_map` は読まない。詳細は既存アプリの `docs/domain/board_teitori.md`
- 計画の同期(60秒ごと)で、`open_readonly` で全件を1回で読み、本アプリの表 `board_teitori`(マイグレーション 0015)に上書きする(`integration/legacy/teitori.py`、`services/teitori_sync.py`)
- キーは (正規化したファイルNo., 正規化した実装ライン)。**面は問わない**(面1と面2は同じ丁取り)。計画との結びつけは、`plans.file_no` と `plans.line_code`(どちらも取り込み時に既存アプリと同じ規則で正規化済み)で行う
- teitori は status が ok のときだけ 1 以上の整数。ok でも整数でなければ `teitori_invalid` にする。ok 以外では丁取り数を使わない。**行が無い組と、知らない status は「不明」として扱い、丁取りを使わない**(status は今後増えうる。既存アプリの 4.1.0 の status は 8 種類: ok、tsv_not_found、ambiguous_tsv、read_error、no_k_row、multi_k、code_not_in_master、teitori_invalid)
- ビューから消えた組の行は消さない(既存アプリも行を消さない)。共有フォルダが読めないとき、既存アプリは何も書かず前の値が残る(`fetched_at` で古さが分かる)
- **ビューが無い(既存アプリが 4.1.0 より前)・読めないときは、同期全体を失敗にしない**。前回の値のまま使い、警告を計画の同期の警告(`plan_sync_warnings`)に出し、起動後の最初の1回だけログに出す(同じ理由では出し直さない)。「読めないDBがあれば同期全体を error」の決まりは、計画と作業者だけに残る
- 丁取りの変化は計画の内容比較(`LegacyPlan.content()`)に入れない。計画の変更として数えず、取消の安全装置にも影響しない
- 管理画面「丁取り」: 丁取りが引けない有効な計画(キッティングNo.、ファイルNo.、ライン、status)の一覧。見るだけ
- 正規化の確かめ(2026-10-31): 既存アプリの `normalize_setup_file_no` / `normalize_mounting_line` のソースを取り出し、実データの月次DB(有効な計画の (ファイルNo., ライン) 500通り)に当てて、本アプリの `domain/normalize.py` と結果が同じ(違い 0 件)なことを確かめた。既存アプリの規則でキーを作ったビューの代わりを読み、実データの全計画(2482行、1771キッティングNo.)が結びついた(結びつかない 0 件、キーが空の計画 0 件)

## 画面・日報・区間 CSV

- ライン画面のバー: 今日の効率(外した計画があれば「対象外 N件」)と、生産中の計画ごとの進捗率。タイムテーブルの枠の「%」も、生産中なら進捗率、そうでなければ「—」
- 日報: その日の効率と、外した計画の件数・理由ごとの件数
- 区間 CSV: 末尾(既存の列の順は変えない)に「目標タクト(秒)」「丁取り数」。工程の行にだけ入る(完了した計画は完了の写し)。丁取りが引けないとき、丁取り数は空。この2列と「生産数」「時間(分)」から効率を Excel で再計算できる(付帯作業と重なる分は「付帯作業」の行から引く)
- 3つとも同じ関数(`efficiency_from_intervals`)と入力(`inputs_for`)を通る。テスト: `test_board_daily_report_and_csv_agree`
