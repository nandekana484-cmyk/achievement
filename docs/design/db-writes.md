# 本アプリのDBへの書き込みの設計メモ

開発指針(docs/spec.md)の 9「書き込みのロック」の背景。対象のコードは `backend/app/db/session.py`(`write_transaction`、`is_busy_error`)と `backend/app/services/idempotency.py`。

## 問題(2026-10-21 の確認で指摘)

SQLite(WAL)は、**古い読み取りにもとづく書き込みを拒否する。** トランザクションを普通の BEGIN(deferred)で始めて読み、その間にほかの接続が書き込んでコミットすると、こちらが書こうとした時点で busy_timeout を待たずに `database is locked`(SQLITE_BUSY_SNAPSHOT)になる。ボタン操作も計画の同期も「読んでから書く」処理なので、同時に動くと失敗しうる。

## 方針

- 本アプリのDBに書き込む処理(ボタン操作、計画の同期、開発用コマンドの追加処理)は `write_transaction(session)` の中で行う
  - 処理の最初に書き込みのロックを取る(`BEGIN IMMEDIATE`)。読む前にロックを持つので、古い読み取りにもとづく書き込みが起きない
  - 同じプロセス内の書き込みは、1つのロック(`threading.RLock`)で1つずつ行う(1プロセスで動かす前提。開発指針 0-7)。同じスレッドの入れ子は許す
  - セッションがすでに読み取りの途中なら、いったん終えてからロックを取り直す
- トランザクションの開始は、SQLAlchemy が pysqlite 向けに示している方法で制御する。接続時に `isolation_level = None` にして pysqlite 自身の BEGIN を止め、`begin` イベントで `BEGIN` か `BEGIN IMMEDIATE` を出す(実行オプションで切り替え)。このため読み取りも明示的な `BEGIN` の中で行うが、WAL なので読み取りが書き込みを止めることはない
- 計画の同期は、既存DBの読み取りと正とするDBの決定をロックの外で行い、反映する部分だけをロックする(既存DBの読み取りに時間がかかっても、ボタン操作を待たせない)
- それでもロックが取れなかったとき(ほかのプロセスが書き込み中など)は 503「他の処理と重なったため、記録できませんでした。もう一度押してください」を返す。冪等性の記録には残さないので、同じ `request_id` で送り直せば記録される
- 計画の同期は、失敗の記録すらできなかったときも例外にせず `result=error`(`sync_run_id` は空)を返し、次の回にやり直す
- 書き込みのロックを待つ時間は `BUSY_TIMEOUT_MS`(10秒)。テストでは短くしてロックの取り合いを起こす

## テスト(tests/test_write_concurrency.py)

- ボタン操作と計画の同期を12スレッドで同時に動かし、500 も 503 も出ないこと、記録が欠けたり重複したりしないことを確かめる
- このテストが効いていることは、ロックと BEGIN IMMEDIATE を一時的に外して確かめた(外すと毎回100件以上が `database is locked` になり、テストが失敗する)
- 別の接続で `BEGIN IMMEDIATE` を持ったままにして、503 になること、送り直すと記録されることを確かめる
