# 表示言語の切り替え(日本語とベトナム語)の設計メモ

開発指針(docs/spec.md)の 7.5 の実装の判断の理由。対象のコードは `frontend/src/i18n/`。

## 仕組み

| ファイル | 役割 |
| --- | --- |
| `ja.ts` | 画面の文言の辞書(基準)。キー → 日本語の文 |
| `vi.ts` | ベトナム語の辞書。型は `Messages`(ja.ts と同じキーをすべて持つ)。キーの抜けや余分なキーは型のエラー(`npm run build` の tsc) |
| `translate.ts` | 差し込み(`format`)、`makeTranslate(lang)`、マスタの名前の選び方(`localName`)。React に依存しない |
| `storage.ts` | 選んだ言語を、その端末の localStorage に記憶する |
| `I18nProvider.tsx` | 今の言語と `t()` を画面に配る(`useI18n()` → `{ lang, setLang, t }`) |
| `LanguageSwitch.tsx` | 「日本語 / Tiếng Việt」のボタン。ライン選択の画面と、ライン画面の上部に置く |

- ライブラリは足さない(文言は200程度で、差し込みと言語の切り替えだけで足りるため。依存を増やさない)
- 差し込みは `{name}` の形。`t("unit.lots", { count: 3 })` → 「3ロット」。渡されていない名前は `{name}` のまま残す(抜けに気づけるように)
- 言語を切り替えると、画面全体を描き直す(Provider の値が変わるため)。読み込み中のデータや、開いているダイアログはそのまま
- 画面から切り離した処理(`steps.ts`、`planMatch.ts`、`timeScale.ts`、`send.ts` など)は、`t` を引数で受け取る(vitest で言語ごとに確かめられるように)
- `<html lang>` と画面のタイトルも、選んだ言語に合わせる

## 端末への記憶

- localStorage の `genba.lang` に `ja` か `vi` を入れる。最初(何も入っていない、知らない値)は日本語
- 読めない・書けない環境(プライベートモード、容量の上限など)でも落ちない。その場合は画面の言語だけ切り替わり、次に開いたときは日本語に戻る
- 端末ごとの記憶なので、同じタブレットを使う人が変わったら、その人が切り替える

## 訳すもの・訳さないもの

| 種類 | 扱い |
| --- | --- |
| 画面の文言(ボタン、見出し、案内、確認の画面、工程と状態の名前、単位など) | 辞書で訳す |
| 端末で作るエラーの文(通信できない、送信中など) | 辞書で訳す |
| サーバーが返すエラーの文(409 / 404 / 503 の detail) | 訳さず、そのまま出す(サーバーの文は日本語。業務ルールの文をサーバーと画面の2か所で持たないため) |
| 計画の内容(キッティングNo.、ロットNo.、基板名、計画の警告)、作業者の名前、ラインの名前 | 訳さない |
| 理由と設備の名前(マスタ) | `name_vi` があればベトナム語、空なら日本語(下記) |
| 日付と時刻 | どちらの言語でも同じ形(「10/21」「9:00」「08:00 〜 08:20」。24時間表記、日本時間) |

## マスタの名前(理由と設備)

- reasons と equipment に `name_vi`(空を許す)を持つ(マイグレーション 0008)
- `/api/masters`、board の付帯作業、工程と付帯作業の操作の応答で、日本語の名前とベトナム語の名前の両方を返す(`reason_name` と `reason_name_vi` など)。どちらを出すかは画面が決める(`localName`)
- 登録は今は開発用のコマンドで行う(`python -m app.cli equipment add S マウンター1 --vi "..."`、`equipment set-vi <ID> "..."`、`reasons set-vi <ID> "..."`。空の文字列で消す)。管理画面のマスタの作業で画面から登録できるようにする

## キーの付け方

- 「画面や部品.項目」の形にする(例: `lineScreen.noOperator`、`ng.stepSide`、`topBar.operatorLabel`)
- 複数の画面で同じ意味で使う文は `common.`(例: `common.cancel`「やめる」、`common.sending`「送信中…」)。単位は `unit.`、工程は `step.<step_type>`、工程の状態は `stepState.<state>`
- 意味が違えば、日本語が同じでも別のキーにする(訳すと違う言葉になることがあるため。例: メニューの `sideMenu.lineEvents` と、パネルの見出しの `lineEvent.title`)
- 文をつなげて作らず、差し込みのある1つの文にする(語順が言語で違うため。例: `restart.title`「{step}の開始」)

## 文言を足すときの手順

1. `ja.ts` にキーと日本語の文を足す
2. `vi.ts` に同じキーを足す(訳が無ければ「(未翻訳)」+ 日本語の文)。足し忘れると `npm run build` が型のエラーで止まる
3. 画面では `const { t } = useI18n();` → `t("キー")`。`.tsx` に日本語の文字を直接書かない

## テスト

- `src/i18n/translate.test.ts`: 差し込み、言語の判定、マスタの名前の選び方
- `src/i18n/storage.test.ts`: 記憶の読み書き(使えない環境も)
- `src/i18n/messages.test.ts`: vi.ts のキーと差し込みの名前が ja.ts と同じこと。キーの抜けと余分なキーが型のエラーになること(`@ts-expect-error`。tsc で確かめる)
- `scripts/no-hardcoded-text.test.ts`: 画面のファイル(`src` の .tsx と .ts。コメント、テスト、辞書、自動生成のAPIの型は除く)に日本語の文字が直接書かれていないこと。node のファイルの読み取りを使うので、tsc の対象の `src` ではなく `scripts` に置く
- Playwright の ⑭: ベトナム語に切り替えたライン画面のスクリーンショット、開き直しても言語が残ること、日本語に戻せること

## ベトナム語の訳

- 訳はレビュー役が用意する。初版(148件)は 2026-10-21 に取り込んだ。現場の用語は、使いながら直す
- 新しく足した文言は、訳が入るまで「(未翻訳)」+ 日本語の文にしておき、レビュー役が置き換える。差し込みの名前(`{count}` など)は変えない(テストで確かめる)
- 文の部品(計画の説明など)を別の文に差し込むところがあるので、訳がまだの文があると「(未翻訳)」が重なって見えることがある
