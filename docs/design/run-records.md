## キッティングNo.の単位(2026-10-21 に変更)

既存アプリの調査結果: 1つのキッティングNo.に複数のロットがある計画が多い(有効な 4,029件のうち 1,143件。最大10ロット)。同じキッティングNo.の中では、ファイルNo.・ライン・面・計画開始・終了は常に同じで、違うのは基板名と数量。現場は1つのキッティングNo.を1回の段取りでまとめて生産する。

- 計画の取り込み(同期)は、既存アプリと同じ「キッティングNo.+ロットNo.」の単位のまま
- 画面と実績(工程の記録・生産数・進捗・備考・完了)は「キッティングNo.」の単位にまとめる(`services/kitting_plans.py`)。計画数はロットの数量の合計
- ロットによって値が違う場合は警告を出し(同期の警告と、計画の `warnings`)、計画開始は最も早いもの、計画終了は最も遅いもの、それ以外は最初のロット(ロットNo.の順)の値を使う
- 一部のロットが取消になったら、残ったロットだけでまとめる。すべて取消ならまとまりも取消(開始はできないが、終了はできる)
- 完了の写しには、その時点のロットの一覧も残す(あとでロットの数量が変わっても、過去の記録が変わらないように)
- マイグレーション 0006 で、それまでの開発用の記録をキッティングNo.の単位に移した(本番にはまだ入れていない)。同じキッティングNo.に複数のロットの工程の記録がある場合は、作り直さずに止める

## NG数(ロットと面)

- **面を区別する理由**: 面1でNGになった基板は面1の部品だけを使い、面2でNGになった基板は両面の部品を使っている。在庫の差異(仕損)を正しく出すには、どの面でNGになったかが必要。既存アプリも NG を「キッティングNo.+ロットNo.+面」で保存している
- 既存アプリでは、面2の計画の画面から、同じロットの面1のNGも入力する。本アプリも同じく、面2の計画では面1を選べる。ただし、同じロットNo.・同じファイルNo.の面1の計画が見つかるときだけ(面1のNGを返す先の計画が無いため)
- 面1の計画では面2は選べない(面2はまだ実装していないので、面2のNGは出ない)
- 記録は `run_ng_inputs`。`kitting_no` は入力した画面の計画、`side_kitting_no` はNGが出た面の計画(面1のNGなら面1の計画)のキッティングNo.。同じ (kitting_no, lot_no, side) は最新の値を有効とし、過去の値は履歴として残す
- **既存アプリへの変換が必要(実績の反映の作業で作る)**: 既存アプリは、面1の計画のNGを「面1の欄 + 面2の欄」の形で持つ(面2の計画で入力した面1のNGも、面1の計画の行に入れる)。本アプリの記録から、`side_kitting_no` ごとに集めて、この形に変換して返す。今回は変換を作っていない

## 冪等性(api_requests)

端末は操作ごとに一意の `request_id` を送る(開発指針 0-5)。

- 初めての `request_id`: 操作を行い、要求の内容(payload)と応答(response)を `api_requests` に記録する
- 同じ `request_id` で同じ内容: 操作はせず、**最初の応答をそのまま** 返す。記録の今の状態を返すのではない(あとで終了されても、開始の再送には開始したときの応答を返す)
- 同じ `request_id` で違う内容(別の操作に使い回した場合も): 409
- ルール違反や書き込みの混雑で失敗した操作は記録しない。同じ `request_id` で送り直せば、もう一度判定する
- 各表の `*_request_id` 列(run_events など)も持つ。どの操作でできた行かを後から追えるようにするため
- 応答の形に項目を足すときは既定値を付ける(項目が無かったころに保存した応答を読み直せるように。例: `RunEventOut.equipment_id`)。要求の内容に項目を足すときも、指定が無いときは前と同じ形にする(例: 工程の開始の `equipment_id` は指定したときだけ payload に入れる)

## 二重の記録の防止

サービスの確認(終了していない記録があるか)に加えて、DBにも部分ユニークインデックスを持たせる。

- `run_events`: キッティングNo.×工程で、終了していない(`end_at IS NULL`)記録は1件まで(取り消した記録は除く。マイグレーション 0011)
- `line_events`: ライン×理由で、終了していない記録は1件まで(取り消した記録は除く)
- `line_operators`: 今の担当者(`end_at IS NULL`)はラインに1人

書き込みは BEGIN IMMEDIATE とプロセス内のロックで1つずつ行うので通常は当たらないが、当たった場合は 409「ほかの操作と同時に行われたため…」にする。

## 作業者(既存アプリの workers の読み込み。services/worker_sync.py)

既存アプリの調査結果: 作業者は master.db の workers 表(worker_id TEXT 主キー、name、role = admin / operator、is_active = 1 / 0)。worker_id は利用者が自由に入力する(32文字まで。形の決まりは無い)。保存は入力したままの表記で、重複は全角・半角と大文字・小文字の違いを無視して判定している(models/workers.py)。削除はせず is_active=0 にする。並び順の列は無い。

- 計画の同期のたびに読み(既存DBを開くのは `integration/legacy/workers.py`)、本アプリの operators に反映する(書き込みのロックの中)
- 作業者IDは表記のまま `worker_id` に、正規化した値を `worker_key` に持つ(呼び出しと重複の判定は `worker_key`)。表記だけが変わった(例: y001 → Y001)場合は同じ作業者として扱う
- 既存アプリから見えなくなった作業者は、消さずに無効にする。過去の記録(工程・NG・担当者の履歴)が参照しているため
- 正規化すると重なるIDは、表記の順で最初の1人だけ取り込み、ほかは取り込まずに警告を出す(どちらが正しいか本アプリでは決められないため)
- 開発用コマンドで足した作業者(source=local)は、既存アプリの読み込みで無効にしない。同じIDの作業者が既存アプリに現れたら、上書きせずに警告を出す。legacy_app_dir が設定されている環境では、開発用コマンドでの追加を断る(本番の作業者は既存アプリが正)
- master.db に workers 表が無いときは、警告を出して作業者は変えない(無効にもしない)
- 作業者は計画とは切り離して読む(`read_master_workers`)。計画の同期がエラーになった回(想定タクトの表が無い、月次DBが無いなど)でも、workers が読めれば作業者は反映する(`sync_operators_alone`。別の書き込み)。その回は警告の記録を変えないので、作業者の警告はログにだけ出す。作業者を使う画面(担当者の交代)は、計画が読めない環境でも使えるようにするため
- マイグレーション 0007 は operators 表を作り直さず、列とユニークインデックスを足す(工程の記録などが作業者を参照しているので、表を作り直すと外部キーで止まるため)
- 並び順の列が無いので、画面の一覧は名前順(同じ名前は作業者IDの順)にする

## 記録者(line_operators.py)

- 本文の `operator_id` を使う。指定が無ければラインの今の担当者。どちらも無ければ 409「担当者が設定されていません」(PIN は付けない。spec.md 11)
- 開始した人と終了した人を別々に持つ(人員交代で変わるため)
- 担当者を「今と同じ人」に交代したときは、行を足さずに今の担当者を返す

## 工程のルールの補足(run_records.py)

- 生産の区切り(seq)はキッティングNo.×工程ごとに1から振る。記録用紙の欄は3つだが、データ上は上限を設けない
- 2回目以降の生産の開始は再開理由が必須。設備が必要な再開理由(マシントラブルなど)では、設備を **任意で** 受け付ける(run_events.equipment_id。計画のラインの設備)。それ以外では受け付けない
- 取消の計画は開始できないが、終了はできる(取消の前に始めた工程を閉じられるように)
- 片付けの終了で完了(run_completions)を作る。生産数は終了した区切りの合計、NG数はその時点の最新。計画数と想定タクトを写して残す(後で計画が変わっても、過去の稼働率や日報が変わらないように)。片付けをやり直したらもう1件作り、最新のものを有効とする(訂正で作り直した行もあるので、「最新」は作った順で決める。完了の時刻の順ではない)
- 稼働率は定義が決まるまで計算しない(utilization は空)

## 付帯作業(line_events.py)

- 付帯作業として使える理由だけ。設備が必要な理由ならそのラインの設備、記入が必要な理由なら記入が必須
- 異なる理由どうしは重なってよい
- 理由は、生産の再開理由と共通のマスタ(reasons)。マシントラブルの合計時間を、計画の中か合間かに関係なく集計できるようにするため

## ライン画面用の取得(board.py)

- その日に計画開始〜終了が重なる有効な計画ごとに、工程の記録・生産数の合計・最新のNG数・最新の完了・計画の進捗率を返す
- 付帯作業は、その日に重なるもの。終了していないものは「今」まで続いているとみなし、今より後の日には出さない
- ラインの進捗率は仮置き(その日の計画の生産数の合計 ÷ 計画数の合計。spec.md 11)。計画数が0なら null

## マスタ

- ラインは計画の同期で自動登録する(名前は「<記号>ライン」)。マイグレーション 0004 で、それまでに取り込んだ計画のラインも登録した
- 作業者・設備の追加は、今は開発用のコマンド(`python -m app.cli`)だけ。管理画面とログインは後で作る
- 行は消さず、使わなくなったものは `active=False` にする

## 実績の訂正(2026-10-22 に追加。現場の画面から)

開発指針 5.4〜5.7 の「訂正」の判断の理由。管理画面からの訂正は次の回で作る(同じサービスを、範囲の制限なし・source=admin で呼ぶ想定。`FieldScope` を渡さなければ範囲を確かめない)。

### 記録を消さずに直す

- 取り消しは行を消さず、`voided_at`・`voided_by`・`void_reason` を付ける(開発指針 0-3)。取り消した記録を計算から外すのは、それを読むところ(`produced_total`、`open_event`、ライン画面に出す計画の条件、完了の有効・無効、画面の工程の状態とタイムテーブル)で行う
- 後からの追加は `added_later` を付け、記録した人(開始・終了の両方)は直した人にする。start_request_id / end_request_id には訂正の request_id を入れる
- 変更の前後は run_corrections の changes_json に項目ごとに残す。run_events には最新の値だけを持つ(読むところを変えずに済むように)
- audit_log(マスタの変更)とは表を分けた。実績の訂正は「どの計画・どのラインの記録か」で引くことが多く、理由の区分や どの画面から を持つため
- 時刻の比較はタイムゾーン付きで行う(送られた時刻のタイムゾーンは問わない。履歴には日本時間で残す)

### 番号(seq)と「何回目」

- seq は「キッティングNo.×工程×seq」の一意制約のための番号で、取り消した記録や後から足した記録でも振り直さない(振り直すと、記録の名前が後から変わり、一意制約を二段階で外す必要もあるため)
- 画面の「生産 N回目」は、取り消していない区切りを開始の順に数えた数(`frontend/src/field/line/steps.ts` の `recordNumbers`)
- 2回目以降の生産の開始で再開理由を求める条件も、「取り消していない生産の区切りがあるか」にした(押し間違いの1回目を取り消したあとの開始は、1回目の扱い)

### 時刻のルール

- 終了していない記録は今も続いているとみなし、同じ工程のほかの記録と重ねない(画面のボタンでは、終了していない記録があるあいだ同じ工程を開始できないのと同じ)。終了した記録どうしは、生産の区切りだけ重ねない(ほかの工程は、やり直しで重なることがあり得るので、今までどおり縛らない)
- 終了していない記録の終了の時刻は直せない。終了は工程のボタンで行う(生産数の入力や完了の作成を、ボタン操作と同じ流れにするため)
- 未来の時刻は不可(時刻の基準はサーバーの時計)

### 現場の画面で直せる範囲

- 開始か終了が「今の稼働日の前後 `corrections.field_margin_hours`(既定12時間)」にある記録だけ。既定はタイムテーブルの表示範囲(48時間)と同じで、現場は自分の見える記録だけを直せる。入れる時刻も同じ範囲の中だけ(現場の画面から遠い過去へ動かせないように)
- 範囲の基準は、記録の日付ではなく **今の稼働日**(タブレットのライン画面は常に今の稼働日を出すため)

### 完了の作り直し(services/completions.py)

- 工程の記録を訂正するたびに `rebuild_after_correction` を呼ぶ。終了した片付け(取り消していないもの)が残っていれば、最後のものをもとに完了の行を足す(kind=correction、correction_id)。残っていなければ何も作らず、完了でない状態になる
- 有効な完了 = 完了にした片付けが取り消されていない行のうち、作った順で最後のもの。片付けの終了を取り消すと、その片付けの完了は無効になる
- 完了の時刻は片付けの終了の時刻(作り直した時刻ではない)。生産数とNG数は今の値。計画数・想定タクト・ロットの一覧は前の完了の写しを引き継ぐ(訂正で、完了したときの計画の写しが今の計画に変わらないように)。前の完了が無い(押し忘れた片付けを足した)ときは今の計画を写す
- 作り直した行が同じ片付けを参照するので、`cleanup_event_id` の一意制約は外した(マイグレーション 0011 で表を作り直した)
- NG数と備考の入力し直しでは作り直さない(指示書のとおり、今の作りのまま)

### 付帯作業の訂正の履歴

- `GET /api/lines/{line_code}/corrections?date=` は、付帯作業の**開始がその稼働日にある**ものの訂正を返す(訂正した日ではない)。24時間の日報で、その日の付帯作業の訂正を出すため

### 画面(frontend/src/field/line/corrections/)

- 時刻は大きなボタン(±1時間・±10分・±1分)で変える。キーボードを出さずに直せるように(タブレットの文字キーボードは画面を大きく隠すため)。今より後になるボタンは押せない
- 送るのは変えた項目だけ(変えていない項目を送ると、履歴に「変わっていない変更」が残るため)。サーバーも、値が同じ項目は履歴に入れず、何も変わらなければ 409
- 訂正の画面は、送信が成功するまで閉じない(テンキーと同じ。失敗の理由は画面の中に出す)
- 直した人はラインの今の担当者。未設定なら、ボタン操作と同じく先に担当者を選ぶ画面を出す(訂正の履歴は見るだけなので担当者は要らない)
